# 项目初始化（lite）

面向个人/小项目的最小初始化：把"想做啥 / 用啥栈 / 大概拆成几个模块"对齐清楚，落盘 3 份必备文档即可进入开发。

---

## AI 行为总纲

- **主动追问、但不轰炸**：所有对用户的询问和升级请求必须采用交互式问答提交给用户；一次问一组相关问题，每组 3~5 条；用户回答模糊时给 2-3 个选项让其挑。
- **技术选型不擅自决定**：多个选项时列出利弊请用户拍板。
- **每阶段产出落盘**：不要只在对话里展示。
- **阶段顺序是建议**：用户已明确目标和技术栈时，可压缩阶段一直接进阶段二。
- **不写业务代码**：本 skill 只产出规划文档。

---

## 阶段一：需求 & 架构对齐（第 1~2 轮对话）

**目标：** 把项目目标、技术栈、核心约定、模块拆分一次性谈清楚，合并产出一份 `docs/需求与架构.md`。

### 1.1 必须问到的维度（可分 1-2 轮问完）

- **项目定位**：一句话描述项目做啥、解决什么问题。
- **核心功能**：用 3~7 条用户故事/功能点说清楚。
- **技术栈**：语言、框架、数据库/存储、关键第三方依赖、版本号（用户没主见时给 2-3 个推荐 + 利弊请拍板）。
- **数据与性能**：预期数据量级、并发/响应时间是否有硬指标（个人项目通常无 → 写"无强要求"即可）。
- **环境与部署**：本地跑、Docker、部署到云？是否需要 `.env`？
- **其他**：是否有权限/认证、是否需要可观测性、是否有合规要求。

### 1.2 模糊处理

用户说"随便"、"你看着办"时，用交互式问答给 2~3 个常见选项 + 一句利弊，请用户挑而不是替他决定。**技术选型必须用户拍板**，不要擅自定。

### 1.3 产出 `docs/需求与架构.md`

```markdown
# 需求与架构

## 项目定位
[一句话]

## 核心功能
- 功能 1：...
- 功能 2：...

## 技术栈
- 语言/框架：
- 数据库/存储：
- 关键依赖（版本号）：

## 核心约定
- ID 策略：UUID / 自增 / 雪花
- 时间格式：ISO 8601 / Unix timestamp
- 错误处理：统一异常类 / 错误码格式
- 日志：级别与格式
- 分页（如适用）：cursor / offset，默认条数

## 系统结构（简明）
- 顶层目录树（src/ 到模块级别即可）
- 关键模块及职责
- 模块依赖关系（文字或 ASCII 图）

## 数据模型（关键实体）
- 实体 1：字段 / 关系
- 实体 2：...

## 接口速查（如有对外接口）
| 接口 | 方法 | 说明 |
|---|---|---|
| /api/auth/login | POST | 登录 |

## 部署与环境
- 启动命令：
- .env.example 关键变量：

## 待确认（用户未拍板项）
- 暂列待办，进入阶段二前必须清空
```

> 接口不再单独成 `docs/interfaces/` 目录。简单项目直接写在本文档"接口速查"段，复杂时再拆出 `docs/接口.md`。

产出后向用户确认："需求与架构已对齐，是否进入模块拆分与脚手架生成？"

---

## 阶段二：拆模块 & 建脚手架（第 3 轮对话）

**目标：** 把架构拆成可执行的 vault 任务，建好目录骨架，落盘 `项目备忘录.md` 与各 `vault/*.md`。

### 2.1 目录结构

```
项目根/
├── 项目备忘录.md         # 中枢文档（< 150 行，软上限）
├── docs/
│   ├── 需求与架构.md      # 阶段一产出
│   ├── 开发进度.md        # 任务追踪表
│   └── 接口.md            # （可选）接口拆出时才建
├── vault/
│   ├── 01-基础脚手架.md
│   ├── 02-数据模型.md
│   ├── 03-XX模块.md
│   └── ...
└── .env.example          # 若项目需要
```

> 与生产版相比，砍掉了 `docs/详细开发流程.md` / `docs/修复记录.md` / `docs/变更单/` / `docs/interfaces/` / `agent-output/`。需要时由具体子 skill 临时建。

### 2.2 `项目备忘录.md` 模板（目标 < 150 行）

```markdown
# 项目备忘录

## 项目概述
一句话描述

## 技术栈
- 简明列表

## 核心约定
- ID / 时间 / 错误 / 日志 / 分页（从 docs/需求与架构.md 摘核心几条）

## 模块依赖图
```
01-基础脚手架
  └─ 02-数据模型
       ├─ 03-认证
       └─ 04-业务A
            └─ 05-业务B
```

## 文档指针
- 需求与架构 → docs/需求与架构.md
- 开发进度 → docs/开发进度.md
- 接口（如有拆出）→ docs/接口.md
- 模块任务 → vault/*.md

## 勿动文件
（已完成且不再改动的模块，初始为空；进入开发后逐步追加）

## Git Commit 规范
- 默认 main 分支线性开发
- 格式：feat/fix/test/refactor/docs/chore(scope): description
- 每完成一个功能点一次提交
```

### 2.3 单个 `vault/XX-模块.md` 模板（目标 < 250 行）

```markdown
# 0X-[模块名]

## 模块做啥（1 行）

## 依赖谁（1 行）
- 必须先完成：vault/0Y、vault/0Z
- 可并行：vault/0W

## 需要先读哪几个文件（2~5 个）
- 项目备忘录.md（必读）
- docs/需求与架构.md「XX 段」
- vault/0Y.md 产出文件
- src/...（已有公共代码）

## 接口与类型
（本模块涉及的接口定义、入参出参、关键类型；直接列在这里，不必跨文件查）

## 实现要点
- 业务逻辑要点
- 必须复用的工具/基类（指明路径）
- 安全/性能注意
- 禁止事项

## 测试要点
- 必须覆盖的场景
- mock 策略

## 产出清单
- src/.../xxx.ts
- src/.../xxx.spec.ts

## 行数预估
- 源码文件目标 < 500 行；> 1000 行必须拆模块
```

> **vault 顶部 3 行**（"做啥/依赖谁/需要先读哪些文件"）是必备硬约束——它让后续开发时主 Agent 不必读全文也能定位。

### 2.4 `docs/开发进度.md` 初始格式

```markdown
# 开发进度

## 状态：⬜ 待开发 | 🚧 进行中 | ✅ 已完成 | 🚫 阻塞

| 编号 | 模块 | 状态 | 依赖 | 备注 |
|---|---|---|---|---|
| 01 | 基础脚手架 | ⬜ | — | |
| 02 | 数据模型 | ⬜ | 01 | |
| 03 | ... | ⬜ | 02 | |
```

### 2.5 快速复核（5 项即可）

- [ ] `项目备忘录.md` 行数 ≤ 150（软上限，超 200 才提示精简）
- [ ] 每个 vault 顶部"做啥/依赖谁/先读哪些文件"3 行齐全
- [ ] vault 编号与依赖关系无悬空
- [ ] `docs/需求与架构.md` 无"待确认"残留
- [ ] `docs/开发进度.md` 含全部 vault 任务

复核通过后提示用户：**"初始化完成，可以直接进入《项目开发》skill 开始编码，或在同一会话里继续，不需要清空上下文。"**

---

## 关键提醒

1. **本 skill 只规划、不编码。**
2. **技术选型让用户拍板**，并且必须用交互式问答提交给用户，不要擅自决定。
3. **文档上限是软约束**：超了打 ⚠️ 提示精简，但不阻塞当前操作。
4. **不强制并行子 agent**：主 Agent 串行问、串行写即可；只有当项目特别大、需要同时调研多个独立模块时才考虑派 1~2 个只读子 agent。

---

## 反模式

- ❌ 用户一句话就出完整规划，跳过追问。
- ❌ 把架构写得很详细，但 vault 没拆 / 没顶部 3 行摘要。
- ❌ 单独建 `docs/interfaces/` 多文件矩阵（本 lite 版不要）。
- ❌ 输出在对话里不落盘。
- ❌ 技术选型自己拍。
