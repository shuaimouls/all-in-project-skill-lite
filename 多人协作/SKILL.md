# 多人协作（lite overlay）

本 skill 是跨阶段的 `ASSISTING/COORDINATING` 协调层，不替代唯一 `ACTIVE` 生命周期 skill。它提供完整指引，但不是无人值守代理：分支选择、负责人、功能冲突、合并策略、push 和清理经常需要用户确认。

## 触发与边界

- 用户明确多人开发、分支归属、协作进度、依赖或合并排序时注入。
- 仅看到多个活跃分支时先询问是否确为多人协作；个人临时、实验或陈旧分支不能自动视为团队工作。
- 只协调、解释和推荐；不修改源码/文档，不 checkout、建分支、merge、rebase、push、删除、reset 或 force。
- 不因 overlay 注入扩大当前 `ACTIVE` skill、用户授权或任务范围。

## 一、建立协作基线

优先复用仓库已有合理约定，不自动改名：

- 实际默认集成分支（不得默认必为 `main`）。
- 分支命名规则、owner、任务/vault 范围。
- 每个分支的 base、依赖分支和共享契约。
- 独立代码审查门禁、测试要求、合并队列。
- Git 是实时状态事实源；`docs/开发进度.md` 记录任务状态。

只有用户需要跨会话记录且仓库没有 tracker 时，才建议新建轻量 `docs/协作状态.md`；仅保存 owner、任务、依赖、目标分支等稳定信息，创建仍需用户授权。

## 二、解释后的进度表

不要向新手倾倒原始 Git 输出。把可信证据整理为：

| 分支 | 负责人 | 用途/范围 | 相对目标分支进度 | 审查 | 测试 | 冲突/依赖 | 建议状态 |
|---|---|---|---|---|---|---|---|

状态图例：

- `Ready`：范围明确，审查与所需测试有当前通过证据。
- `Needs review`：实现可能完成，但尚无独立审查结论。
- `Blocked`：依赖未集成、测试失败或存在待裁决冲突。
- `Unknown`：缺少当前证据；不得把历史通过当当前通过。
- `Already integrated`：变更已在目标分支中，需以提交/内容证据确认。

## 三、推荐与逐支授权

根据依赖与 readiness 推荐合并顺序并说明理由。普通模式下用交互式问题让用户选择；Goal 模式下按启动合同中已确认的分支清单和顺序连续推进，无需逐支重复询问：

1. 合并推荐分支；
2. 先审查某个分支；
3. 先处理阻塞或冲突。

每次授权只覆盖一个明确分支。普通模式下，一个分支完成后刷新全表，再询问下一项，不把一次“继续”解释成批量授权。Goal 模式只可按启动合同明确列出的分支、base、顺序和动作连续处理；出现新分支、顺序变化、功能冲突或新的机械冲突方案时交回 Goal 作为超范围阻断。未审查分支先交《代码审查》，明确源/目标后才交《分支合并》。

## 四、功能冲突门禁

以下不一致属于功能/意图冲突：业务规则、公共 API/类型、数据库迁移、权限安全、配置语义、共享模块归属、测试期望。

发现时立即停止后续写操作，向用户展示：

- 双方行为和分支/文件/提交证据；
- 下游影响与兼容风险；
- 2–3 个中立方案及取舍；
- 推荐项（可以推荐，但不能代替用户决定）。

用户拍板后把决定传回当前 `ACTIVE` skill；必要时先走《需求修改》《Bug修复》或《重构协调》。

## 完成标准与反模式

- 分支、owner、范围、base、依赖、审查和测试状态均有来源或标为未知。
- 合并顺序可解释，且下一动作只涉及一个分支。
- 未获得任何代码修改或 Git 写权限。

反模式：误判多人；默认目标为 `main`；倾倒原始 Git 输出；一次授权连续合并多支；把功能冲突当机械冲突；把审查通过等同于 merge/push；合并后自动删分支。
