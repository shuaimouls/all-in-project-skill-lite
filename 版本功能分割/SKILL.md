# 版本功能分割（lite）

> 本 skill 负责版本规划和 TODO 映射，不写业务代码。用户确认分割结果前不得修改项目文件。

## 适用场景

- 《最小上线标准评估》已输出并由用户确认，或用户明确要求调整版本路线。
- 需要将功能按上线顺序写入 `docs/开发进度.md` 和 `vault/`。

## 状态机

```text
LOAD → DRAFT V0/V1/V2 → DEPENDENCY CHECK
→ USER_CONFIRM → SYNC DOCS → CROSS-CHECK
```

## 分割原则

- 用可独立验证的用户价值纵向切片组织版本；首个可上线版本必须形成完整核心闭环。
- 版本内先满足依赖，再按上线阻断级别排序。
- V0 是最快上线范围，V1 补齐完整体验，V2 承载扩展增长；版本名称可按项目约定替换，但语义必须保留。
- 每个版本都要有目标、包含功能、明确不包含、依赖和上线标准。
- 未来版本不得偷改当前版本验收标准；后续任务提前实现仍保留原版本归属。

## 文档同步

用户确认后按以下顺序串行同步：

1. `docs/需求与架构.md`：版本路线、V0 最小上线标准、各版本明确不包含项。
2. `vault/*.md`：依赖摘要后增加“版本归属与上线关系”，写目标版本、目标/闭环、是否阻断上线、验收标准和扩展点。
3. `项目备忘录.md`：只保留当前目标版本和规划文档指针，不复制完整矩阵。
4. `docs/开发进度.md`：任务表增加 `版本/批次`、`上线阻断`、`验收/证据` 列，按版本和依赖形成真实 TODO 顺序。
5. `docs/接口.md` 或 `.env.example`：仅在版本切分改变接口或配置时同步。

跨多个版本且尚未开始的任务应拆分；已完成任务使用 `02a-*.md` 等增量返工任务保留历史。已进入确认版本或已有实现证据的任务不得直接删除，应标记取消、移版或增量返工。

## 输出格式

```markdown
## 版本功能分割
| 版本 | 目标 | 功能/任务 | 明确不包含 | 上线标准 |
|---|---|---|---|---|

### 依赖核对
- V0 依赖：
- 跨版本依赖：
- 阻断任务：

### TODO 同步计划
- 开发进度：
- vault：
- 备忘录：
- 接口/配置：
```

## 完成检查

- [ ] 每个任务恰有一个当前版本归属
- [ ] 版本目标与功能/任务一致
- [ ] V0 形成完整闭环
- [ ] 依赖无悬空或环路
- [ ] 上线阻断级别和验收标准可追踪
- [ ] 已完成历史未被覆写
- [ ] 用户确认已先于文件写入

## 反模式

- ❌ V0 只做数据库、API 或 UI，无法独立验证用户价值。
- ❌ 把任务表顺序当作版本顺序而忽略依赖。
- ❌ 静默删除已承诺或已实现的任务。
- ❌ 通过把失败任务移到 V1 伪造 V0 达标。
