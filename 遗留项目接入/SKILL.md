# 遗留项目接入 Skill

本 skill 用于把一个**已有源码、但缺少本套件脚手架文档**的项目，逆向梳理并补齐为标准脚手架（`docs/`、`vault/`、`项目备忘录.skill`），从而能直接被《项目开发.skill》驱动继续开发。

与《项目初始化.skill》的本质区别：
- 初始化是**从无到有**，需求来自用户问答；
- 本 skill 是**从代码反推文档**，事实来自既有源码，用户只做确认与补缺。

---

## 适用场景

**触发条件：**
- 工作目录**已有可观的源代码**（非空白、非仅含 README/.gitignore）。
- `项目备忘录.skill`、`docs/`、`vault/` **至少有一项缺失或不完整**。
- 用户表述为"接入已有项目""给老项目补文档""让这个仓库能用项目开发 skill""逆向生成脚手架"等。

**不适用：**
- 空白文件夹从零启动 → 使用《项目初始化.skill》。
- 脚手架已完整、只是要继续写代码 → 直接用《项目开发.skill》。
- 脚手架已完整、只是需求变更 → 使用《需求修改.skill》。

---

## AI 行为总纲

- **代码为事实源**：所有文档内容必须从真实代码、配置、依赖清单中提炼，**严禁凭空臆造**需求或架构。
- **不改业务代码**：本 skill 只产出/补齐文档，不重构、不修改任何源码。
- **多子 agent 并行扫描**：阶段二的代码扫描必须按模块/层次拆分，**并发派发**给只读调研子 agent，主 Agent 只做调度与汇总（参考《需求修改.skill》阶段二的并发模式）。
- **存疑必问**：所有对用户的询问和升级请求必须采用交互式问答提交给用户；从代码推断不出的信息（业务意图、性能目标、未来规划），列为"待确认项"逐一向用户求证，禁止填充虚假默认值。
- **产出全部落盘**：不能只在对话里展示，必须写入指定路径。
- **严格按阶段执行**：阶段 1 → 2 → 3 → 4 → 5 不可跳过，每阶段产出后向用户确认。

---

## 前置条件检查（AI 启动后必须做）

- [ ] 工作目录存在源代码文件（如 `src/`、`app/`、`lib/` 或语言相关入口文件）。
- [ ] 存在可识别的依赖/构建清单（如 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml`、`Cargo.toml` 等）之一。
- [ ] 确认 `项目备忘录.skill` / `docs/` / `vault/` 的缺失情况（决定本次需补齐的范围）。

若工作目录实际为空或几乎为空 → 停止，提示用户改用《项目初始化.skill》。

## 阶段一：项目勘探与基线确认（第 1 轮对话）

**目标：** 在大规模扫描前，先建立项目全貌的基线认知，并与用户对齐范围。

**AI 必须完成：**
1. 识别**技术栈**：语言、框架、运行时、数据库、中间件（从依赖清单与配置文件读取，标注版本号）。
2. 识别**项目类型与入口**：CLI / Web 服务 / 库 / 全栈应用，主入口文件、构建/启动脚本。
3. 识别**顶层目录结构**：列出一级/二级目录及其疑似职责。
4. 评估**测试现状**：是否已有测试目录、测试框架、大致覆盖情况。
5. 统计**已存在的脚手架文档**：哪些已有（如 README、已有 docs）、哪些缺失。

**向用户确认的基线问题（必须用交互式问答提交；按需追问，缺一不可补全文档的，必须问）：**
- 项目的一句话定位与核心业务目标？（代码通常推不出业务意图）
- 是否有未在代码中体现的性能/安全/合规要求？
- 是否有已知的"勿动"模块或历史包袱（不希望被后续 Agent 改动的部分）？
- 接入后近期希望继续开发/重构哪些方向？（用于后续 vault 任务优先级）

**产出物（落盘）：**
```
docs/接入勘探报告.md
```

勘探报告模板：
```markdown
# 接入勘探报告

## 项目基线
- 项目定位：[用户确认的一句话描述]
- 技术栈：语言/框架/数据库/中间件/版本号
- 项目类型与入口：[类型] / 入口文件 / 启动命令
- 构建与依赖管理：[工具]

## 顶层结构与疑似职责
| 目录/文件 | 疑似职责 | 备注 |
|---|---|---|

## 测试现状
- 测试框架：
- 测试目录：
- 大致覆盖：

## 已有脚手架文档盘点
| 目标文档 | 现状（已有/缺失/不完整） | 处理计划 |
|---|---|---|
| 项目备忘录.skill | | |
| docs/项目需求.md | | |
| docs/架构设计.md | | |
| docs/interfaces/ | | |
| vault/ | | |
| docs/开发进度.md | | |

## 待确认项（代码推断不出，需用户回答）
1. ...
```

产出后向用户确认：**"勘探报告已生成并确认基线，是否进入代码深度扫描阶段？"**

## 阶段二：代码深度扫描（第 2 轮对话，**多子 agent 并行调研**）

**目标：** 通过并发只读子 agent 把代码事实结构化提取出来，作为后续文档的素材，**不修改任何文件**。

### 2.1 调度策略

主 Agent **不亲自通读全部源码**，而是按扫描域拆分，**一次性并发派发**给多个只读调研子 agent（角色：扫描 Agent，禁止写文件）。每个子 agent 只关注一个域，返回结构化片段，由主 Agent 汇总。

**派发原则：**
- 各扫描域之间无依赖 → 必须并行派发（单条消息内多次调用 search / Task 子 agent）。
- 每个子 agent 的输入：阶段一勘探报告 + 本域扫描范围 + 本域产出格式要求。
- 子 agent 严格只读，禁止越界扫描其他域，禁止臆造未在代码中出现的内容。
- **子 agent 中断处理**：若某个 S-* 扫描子 agent 因超时/断流/异常退出**未交付片段即中断**，主 Agent 不得自己顶替完成该域扫描，必须**针对该域重新 spawn 一个全新的扫描子 agent**继续；其它已返回的片段照常汇总。

### 2.2 扫描子 agent 任务分解

| 子 agent（扫描域） | 扫描范围 | 期望返回片段 |
|---|---|---|
| S1 模块拆分 | 业务源码目录（src/app/lib 等） | 按目录/包识别功能模块，输出模块清单、各模块职责与边界、模块间依赖关系 |
| S2 接口与数据模型 | 路由/控制器/DTO/ORM 模型/schema | 对外接口清单、请求响应类型、数据实体与字段、错误码体系 |
| S3 全局约定 | 配置、公共工具、异常基类、日志/分页/ID 实现 | 实际使用的 ID 策略、时间格式、错误处理、日志、分页等约定（**从代码归纳而非规定**） |
| S4 配置与环境 | `.env*`、配置文件、构建脚本、容器文件 | 环境变量清单、构建/启动/部署方式 |
| S5 测试与质量 | 测试目录、lint/格式化配置、CI 文件 | 测试框架、已有测试覆盖的模块、代码风格工具配置 |

> 扫描子 agent 必须区分"代码中明确存在的事实"与"推断"，推断项单独标注 `(推断)`，供主 Agent 与用户复核。

### 2.3 子 agent 提示词模板（主 Agent 派发时使用）

```
你是扫描 Agent（S[编号]：[扫描域]）。任务：
1. 阅读基线：docs/接入勘探报告.md
2. 仅扫描以下范围：[本域扫描范围]
3. 严禁修改任何文件，严禁扫描范围外内容
4. 只提取代码中真实存在的事实；任何推断必须标注 (推断)
5. 返回结构化 Markdown 片段，格式见：[本域产出格式]
6. 发现矛盾、坏味道或无法理解的设计，单列"需主 Agent/用户确认"段
```

### 2.4 主 Agent 汇总

主 Agent 收齐全部子 agent 返回后：
- 合并为统一的代码扫描汇总（落盘）。
- 将所有 `(推断)` 项与"需确认"段整理成待确认清单，必要时回到阶段一向用户求证。
- 检测跨域一致性（如 S2 接口 vs S1 模块归属是否吻合）。

**产出物（落盘）：**
```
docs/接入扫描汇总.md
```

产出后向用户确认：**"代码扫描汇总已生成（含待确认项 N 条）。请确认推断项，是否进入脚手架文档生成阶段？"**

**待确认项未澄清前禁止进入阶段三。**

## 阶段三：脚手架文档生成（第 3 轮对话）

**目标：** 基于扫描汇总与用户确认，**逆向生成《项目开发.skill》所需的全部脚手架文档**，结构与《项目初始化.skill》阶段三完全对齐。

### 3.1 目标目录结构与文件清单

```
项目根目录/
├── 项目备忘录.skill               # 项目中枢文档（< 200 行）
├── docs/
│   ├── 接入勘探报告.md            # 阶段一产出
│   ├── 接入扫描汇总.md            # 阶段二产出
│   ├── 项目需求.md                # 从现有功能逆向归纳（标注「逆向梳理，非原始需求」）
│   ├── 架构设计.md                # 描述【现状】架构（as-is），含技术决策的事后说明
│   ├── 详细开发流程.md            # 后续迭代路线图（基于用户接入后的目标）
│   ├── 开发进度.md                # 现有模块标 ✅ 已完成（存量），新任务标 ⬜
│   ├── 修复记录.md                # 初始为空表头
│   ├── 变更单/                    # 空目录（供《需求修改.skill》使用）
│   └── interfaces/                # 从现有接口/类型逆向拆分
│       ├── _index.md
│       ├── common.md
│       └── ...（按模块）
├── agent-output/
│   ├── transition/
│   └── request/
├── vault/                         # 见 3.2 存量 + 增量任务规范
│   ├── 00-存量-XX模块.md          # 存量模块的"现状档案"
│   ├── 10-XX新任务.md             # 接入后要做的新开发任务
│   └── integration/
└── .env.example                   # 若缺失，从 S4 环境变量清单逆向补齐
```

> 复用《项目初始化.skill》的所有模板规范：vault 文件规范（3.1）、集成测试规范（3.2）、项目备忘录结构（3.3）、接口拆分策略（3.4）、文档体积控制（3.5）、开发进度初始格式（3.6）。本 skill 不重复抄写，**直接引用**那些模板，仅说明遗留场景下的差异。

### 3.2 vault 的"存量 / 增量"双轨规范（本 skill 特有）

遗留项目已有大量已实现代码，因此 vault 分两类：

**A. 存量模块档案（编号 `00-存量-XXX`）**
为每个识别出的现有模块生成一份"现状档案"，用于让后续 Agent 理解既有实现，而非要求重写：
```markdown
# 00-存量-[模块名称]

## 模块概述
现状职责与边界（来自 S1）

## 现有实现文件
- src/.../xxx（已存在，勿重写）

## 现有接口与类型
（从 docs/interfaces/ 对应文件摘录）

## 已知约束与坏味道
- 当前实现的约定、限制、技术债（标注 (推断) 的需用户确认）

## 测试现状
- 已有测试文件 / 缺失测试的部分

## 状态
✅ 存量已完成（默认进入勿动清单；若计划重构则另建增量任务）
```

**B. 增量开发任务（编号从 `10` 起）**
针对用户接入后想做的新功能/重构/补测试，按《项目初始化.skill》3.1 节标准 vault 模板编写，明确"最小上下文清单"中需读取的存量文件。

> 编号约定：`00-`~`09-` 留给存量档案，`10-` 起为增量任务，避免与存量混淆。

### 3.3 开发进度.md 的存量标记

采用《项目初始化.skill》3.6 节格式，但：
- 存量模块行直接标 `✅ 已完成`，备注注明"存量，逆向接入"。
- 增量任务行标 `⬜ 待开发`。
- 顶部暂不标"阶段四复核已完成"，留待本 skill 阶段五。

### 3.4 项目需求.md / 架构设计.md 的遗留声明

两份文档顶部必须加一行声明：
```markdown
> 本文档为对【现有代码库】的逆向梳理（as-is），非项目原始需求/设计。标注 (推断) 处需持续校正。
```

产出后向用户确认：**"脚手架文档已生成，是否进入交叉校验阶段？"**

## 阶段四：代码-文档交叉校验（第 4 轮对话）

**目标：** 确保逆向生成的文档与真实代码**一致、无悬空、无臆造**。

主 Agent 逐项校验并向用户报告：
- [ ] `docs/interfaces/` 中的接口/类型与源码中真实定义一致（抽样核对关键模块）。
- [ ] 每个存量 vault 档案引用的 `现有实现文件` 路径真实存在。
- [ ] `项目备忘录.skill` 的"项目结构""模块依赖关系"与 S1 扫描结果一致。
- [ ] `.env.example` 覆盖 S4 列出的全部环境变量，无遗漏、无虚构项。
- [ ] 技术栈版本号与依赖清单一致。
- [ ] 所有 `(推断)` 项要么已被用户确认转为事实，要么明确保留标注。
- [ ] 不存在悬空引用（文档指向的文件/模块均真实存在）。
- [ ] 文档体积：项目备忘录 < 200 行、vault < 300 行、interfaces 单文件 < 200 行。

发现不一致 → 主 Agent 直接修正对应文档（必要时重新派发对应扫描子 agent 复扫），不修改源码。

校验完成后向用户确认：**"交叉校验完成，是否进入复核交接阶段？"**

## 阶段五：复核与交接（第 5 轮对话）

**目标：** 确认脚手架完整，使项目可被《项目开发.skill》直接驱动。

**复核清单（逐项检查并向用户报告）：**
- [ ] `项目备忘录.skill` 存在且 < 200 行，文档指针全部有效。
- [ ] `docs/` 必备文档齐全（需求/架构/开发进度/修复记录/interfaces/_index）。
- [ ] `vault/` 含存量档案 + 至少一个增量任务（若用户有接入后目标）。
- [ ] `docs/开发进度.md` 正确区分存量 ✅ 与增量 ⬜。
- [ ] `agent-output/transition/`、`agent-output/request/`、`docs/变更单/` 目录已建。

**复核完成后：**
1. 修正所有遗留问题。
2. 在 `docs/开发进度.md` 顶部标注："✅ 遗留项目接入复核已完成，可进入开发阶段"。
3. 提示用户：**"遗留项目接入完成。请清空上下文后，将《项目开发.skill》与《项目备忘录.skill》一同丢给 AI，从开发进度中拾起增量任务继续开发。推荐优先任务编号：[xxx]"**

## 关键提醒

1. **代码是唯一事实源**：文档内容来自代码，业务意图来自用户确认，**绝不臆造**。
2. **本 skill 不改一行业务代码**，只产出/补齐文档。
3. **存量与增量分轨**：存量模块默认进勿动清单，不要求重写；新增需求才建增量 vault。
4. **推断项必须显式标注并求证**，未确认前不得当作事实写入需求/架构。
5. **对齐既有套件模板**：vault/备忘录/接口/进度的格式直接复用《项目初始化.skill》的规范，保证与《项目开发.skill》兼容。
6. **遇到无法从代码与用户处确定的取舍**，用交互式问答列 2-3 个方案 + 利弊请用户拍板。

## 反模式与 FAQ

**反模式（禁止）**
- ❌ 不扫描代码就凭项目名臆想需求和架构。
- ❌ 把"现状架构"写成"理想架构"，与真实代码脱节。
- ❌ 阶段二让单个 agent 串行通读整个仓库，不做并发拆分。
- ❌ 把存量模块当作待开发任务，要求 Agent 重写已有实现。
- ❌ `.env.example` 虚构不存在的环境变量，或遗漏真实变量。
- ❌ `(推断)` 项未经用户确认就当事实写入文档。
- ❌ 跳过交叉校验，留下指向不存在文件的悬空引用。
- ❌ 在本 skill 内动手改业务代码。
- ❌ S-* 扫描子 agent 因超时/断流/异常退出未交付片段时，**主 Agent 自己顶替扫描、代写模块清单/接口归纳**（必须重新 spawn 新子 agent；中枢文件由主 Agent 串行收尾除外）。
