# 重构协调（lite）

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时分类重构并决定交接路线；作为 `ASSISTING` 时只判断指定候选的类型和影响。重复加载复用既有候选与边界，不主动扩展扫描；本 skill 不因外部建议自动取得代码修改权。

本 skill 是《需求修改》和《项目开发》之间的**协调层**：当用户提出的变更不只是改一个功能点，而是涉及架构重构、模块边界调整、现有设计推翻、已完成模块返工时，先用本 skill 判断该先改文档还是先改代码，并给 AI 一条稳定的执行路线。

---

## 适用场景

- 项目已完成初始化或遗留接入，`项目备忘录.md`、`docs/`、`vault/` 已就位
- 用户提出"重构项目"、"重新设计 XX"、"把现有方案改成 YY"、"拆分/合并模块"、"调整架构"、"之前的设计不合适"等
- 变更会影响多个 vault、多个已完成模块、接口契约、数据模型、技术栈或目录结构
- 用户需要 AI 判断：这到底该走《需求修改》、直接走《项目开发》，还是两者串联
- 已从《重构机会寻找》选中一个或多个 `RF-*` 候选，需要确认类型、执行边界和验证路线

**不适用：**
- 空项目还没规划 → 用《项目初始化》
- 老项目未接入脚手架 → 用《遗留项目接入》
- 明确运行时报错或测试失败，且需求不变 → 用《Bug修复》
- 只改一个未完成 vault 的实现细节，且不影响设计文档 → 直接用《项目开发》
- 用户还没有具体重构目标，只想主动寻找技术债和候选优先级 → 用《重构机会寻找》

## 前置检查

- [ ] `项目备忘录.md` 存在
- [ ] `docs/需求与架构.md` 存在
- [ ] `docs/开发进度.md` 存在
- [ ] `vault/` 下有模块任务

任一缺失 → 停止，提示用户先走《项目初始化》或《遗留项目接入》。

---

## 一、先分类：需求变更、设计重构、实现重构

收到重构/修改现有设计类请求后，先在对话里用 3 类判断，不要急着改文件：

| 类型 | 判断标准 | 下一步 |
|---|---|---|
| 需求变更 | 用户目标、业务规则、接口语义、数据字段、技术栈目标发生变化 | 先走《需求修改》同步文档，再回《项目开发》 |
| 设计重构 | 业务目标不变，但模块边界、目录结构、架构分层、接口形态需要调整 | 本 skill 先产出重构影响清单，再按需调用《需求修改》落文档，最后回《项目开发》 |
| 实现重构 | 文档与设计不变，只是代码可维护性、抽象、重复逻辑、文件过大需要整理 | 直接走《项目开发》的已完成模块修改规则和测试规则 |

如果三类混在一起，按最重路径处理：**需求变更 > 设计重构 > 实现重构**。

---

## 二、重构影响清单（对话内完成）

主 Agent 先读最小必要上下文：

```
L1：项目备忘录.md
L2：docs/需求与架构.md、docs/开发进度.md
L3：受影响 vault 与关键代码文件
```

然后在对话里列清：

若输入来自《重构机会寻找》，先复用候选摘要中的 `RF-*` ID、证据与分数、建议边界、明确不包含、行为保持要求、风险与测试保障、验证范围和文档/接口影响。只补做协调判断和必要抽查，不重新主动寻找候选。候选分数只表示诊断优先级，不代表用户已授权修改，也不得顺手纳入其他观察项。

```markdown
## 本次重构协调结论

### 变更类型
- 类型：需求变更 / 设计重构 / 实现重构 / 混合
- 原因：[为什么这么判断]

### 影响范围
| 对象 | 当前状态 | 影响 | 处理方式 |
|---|---|---|---|
| docs/需求与架构.md | 已存在 | 架构分层调整 | 先由《需求修改》更新 |
| vault/03-认证.md | ✅ 已完成 | 接口签名变化 | 建 03a 返工任务 |
| src/auth/* | 勿动文件 | 需要返工 | 从勿动清单暂时移除 |

### 执行路线
1. 先同步文档：[列出要改的文档/vault]
2. 再进入开发：[列出要实现或返工的 vault]
3. 最后验证：[列出需要跑的测试范围]

### 需要用户确认的问题
- [只有存在技术取舍、需求矛盾、返工范围不明确时才列]
```

需要用户确认的问题必须用交互式问答提交。用户确认前，不改业务代码；如涉及需求或设计文档变化，也不改文档。

---

## 三、调用《需求修改》的条件

命中以下任一条，必须先转《需求修改》：

- `docs/需求与架构.md` 需要更新
- `docs/接口.md` 或 vault 的「接口与类型」需要改变语义或签名
- `docs/开发进度.md` 需要新增、删除、回退或拆分任务
- `项目备忘录.md` 的模块依赖图、勿动文件、文档指针需要更新
- 已完成模块因新设计需要返工，需要新增 `0Xa-*.md` 子任务

转入《需求修改》时，把第二节的影响清单作为输入，并要求它只做文档同步，不写业务代码。

---

## 四、调用《项目开发》的条件

以下情况可以进入《项目开发》：

- 《需求修改》已同步完文档和 vault
- 本次只是实现重构，不涉及需求或文档变化
- 已完成模块需要按新 vault 返工，且返工范围已明确
- 勿动文件已经按规则临时移除，相关依赖测试范围已列出

进入《项目开发》时，必须指定一个明确任务入口：

```markdown
请按《项目开发》继续：
- 当前任务：vault/0Xa-xxx.md
- 需要先读：项目备忘录.md + 该 vault 顶部列出的文件
- 注意事项：本轮是重构/返工，不要顺手优化无关模块
- 验证范围：[模块测试 + 下游依赖测试]
```

---

## 五、重构执行规则

1. **先边界后代码**：先确认哪些设计、接口、模块边界会变，再进入编码。
2. **先文档后实现**：只要设计文档或 vault 会变，就先用《需求修改》落盘。
3. **返工用子任务**：已完成模块优先建 `0Xa-*.md`，不要直接覆盖原 vault。
4. **勿动清单要临时解锁**：涉及 `项目备忘录.md` 的勿动文件时，先移除，验证通过后再加回。
5. **测试范围要扩大到下游**：不只跑被改模块测试，还要跑依赖它的模块测试。
6. **不扩大重构范围**：发现无关坏味道只记录在对话里，除非用户确认，不顺手改。
7. **两次不稳就停**：同一重构问题修 2 次仍不通过，用交互式问答列 2-3 个方案让用户选。

## 六、推荐串联流程

### 6.1 需求或设计变化明显

```
重构协调
→ 列影响清单并让用户确认
→ 需求修改：同步 docs / vault / 备忘录 / 进度
→ 项目开发：按新增或返工 vault 编码
→ 测试与修复
→ 更新进度和勿动清单
```

### 6.2 只有代码结构整理

```
重构协调
→ 确认为实现重构
→ 项目开发：按已完成模块修改规则执行
→ 跑模块测试和依赖测试
→ 更新勿动清单
```

### 6.3 用户只说"重构一下"

先用交互式问答追问 2-3 个选项：

- 目标是改变产品/功能规则吗？
- 目标是调整架构、模块边界或接口设计吗？
- 目标只是整理代码结构、减少重复、拆大文件吗？

用户未确认前，不猜测重构方向。

---

## 七、完成后输出

完成协调后告诉用户：

```markdown
重构协调完成。
- 类型：[需求变更/设计重构/实现重构/混合]
- 已同步：[哪些文档或 vault]
- 下一步：[建议进入《项目开发》的 vault]
- 验证范围：[需要跑哪些测试]
- 风险点：[仍需用户注意的兼容性或返工点]
```

---

## 反模式

- ❌ 用户说重构就直接大改代码。
- ❌ 设计已经变化，却跳过《需求修改》不更新 docs/vault。
- ❌ 把已完成 vault 原地大改，导致历史任务失真。
- ❌ 忽略 `项目备忘录.md` 的勿动文件，直接改稳定模块。
- ❌ 重构时顺手修一堆无关问题，导致验证范围失控。
- ❌ 只跑当前模块测试，不跑受影响的下游依赖测试。
- ❌ 收到一个 `RF-*` 候选后扩大为全仓重构，或把诊断分数当作用户审批。
- ❌ 重复执行完整候选扫描，而不是复用已有证据并做必要抽查。
- ❌ 候选已表现为明确行为缺陷，仍包装成重构而不转《Bug修复》。


## 多人协作门禁

多人模式下先向《多人协作》登记重构范围、owner、base、依赖分支和共享契约。若重构与活跃分支在公共 API、数据库迁移、权限安全、配置语义、模块归属或测试期望上冲突，立即停止并请用户裁决，不能用结构“更优”替代产品决定。实现完成后仍走独立《代码审查》；本 skill 不合并自己的重构分支，合并必须由用户逐支授权《分支合并》。
