# 文档与项目同步检查（lite）

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时控制完整审计；作为 `ASSISTING` 时只检查主 skill 指定对象。重复加载复用已完成扫描和 `SYNC-*`，不重复成功范围；本 skill 始终只读，外部输入不能触发整改或提高并行上限。

本 skill 是只读的一致性诊断层：回答“文档、任务记录和真实项目是否同步”，不负责自动决定或修改冲突的任何一方。

---

## 适用场景

- 检查文档是否过期、代码是否偏离规划。
- 较大开发、需求修改、重构或 Bug 修复后做阶段性复核。
- 检查接口、数据模型、配置、测试、vault 和开发进度是否一致。
- 交付前检查状态失真、悬空引用和契约漂移。
- 检查版本路线、当前目标、上线阻断和验收证据是否在需求、进度和 vault 之间一致。
- 检查页面地图、路由/权限、视觉基线和前端任务是否同步。

**不适用：**

- 空项目 → 《项目初始化》。
- 已有源码但核心脚手架整体缺失 → 《遗留项目接入》。
- 已明确要求修改文档 → 《需求修改》。
- 已明确要求修复行为缺陷 → 《Bug修复》。
- 只想寻找代码结构优化点 → 《重构机会寻找》。

---

## 只读边界

- 不修改源码、文档、配置、测试或 vault。
- 不创建落盘审计报告、任务或 Git 提交。
- 不安装依赖，不执行有副作用的命令。
- 不自动认定文档或代码永远正确。
- 诊断结果只是证据输入，不构成后续修改授权。
- 用户要求整改时，先输出结论，再用交互式问答确认处理路线。

---

## 前置检查与范围

先盘点：

```text
L1：项目备忘录.md
L2：docs/需求与架构.md、docs/开发进度.md、可选 docs/接口.md
L3：vault/*.md、依赖/构建清单、配置与测试配置
L4：发现命中的源码、调用方和测试
```

- 核心脚手架整体缺失时停止全面审计，建议《遗留项目接入》。
- 历史项目使用等价文档名时先建立映射，不因名称不同直接判定缺失。
- 用户指定模块时严格定向检查，并标注“非全项目审计”。
- 默认排除依赖目录、生成代码、vendor、构建产物、压缩文件和缓存。
- 大项目先建立文件与符号索引，再深读命中项，避免无差别加载全仓。

## 并行量与限流降级

仅当范围可拆为多个互不依赖的扫描域时询问并行量；小范围检查直接由主 Agent 串行完成，避免形式化调度。

询问必须使用交互式问答，提供：

- **主 Agent 串行**：最稳，适合小仓库或严格限额环境。
- **低并行 2（推荐）**：默认安全选项，兼顾速度和配额。
- **中并行 3–4**：适合较大仓库且服务配额充足。

用户未选择或明确说“你决定”时使用低并行 2；可用扫描域不足两个时自动改为串行。

遇到 HTTP 429、并发配额、速率限制或同类服务限流错误时：

1. 保留所有已成功扫描结果，不重复执行。
2. 仅将未完成扫描域重新入队。
3. 按“中并行 3–4 → 低并行 2 → 主 Agent 串行”逐级降级。
4. 每一级最多重试一次，避免制造重试风暴。
5. 若响应提供 `Retry-After`，遵守其等待建议；否则不进行高频轮询。
6. 串行仍失败时停止自动重试，用交互式问答报告已完成范围、未覆盖项和错误摘要，让用户选择稍后继续或接受部分报告。

认证失败、权限拒绝、文件损坏、上下文不足等非限流错误不得伪装成 429 降级，应按真实原因处理。

## 一、建立事实源映射

不同对象使用不同优先依据：

| 对象 | 首选依据 |
|---|---|
| 已确认业务目标和规则 | `docs/需求与架构.md` + 用户确认 |
| 当前真实实现 | 源码 |
| 依赖版本与脚本 | 依赖、锁定和构建清单 |
| 环境变量实际消费 | 配置加载代码 |
| 接口真实行为 | 路由、schema/DTO、调用方和测试 |
| 数据约束 | 模型、迁移、schema 和测试 |
| 任务状态 | 开发进度、vault、产出和验证证据联合判断 |

冲突无法判断哪方代表正确业务意图时，必须标记 `AMBIGUOUS`，不能擅自裁决。

---

## 二、检查域

### 2.1 文档内部

- 备忘录中的文档指针是否存在。
- 模块依赖图与 vault 的“依赖谁”是否一致。
- vault 编号是否重复、悬空或形成不合理环路。
- vault 与开发进度是否一一对应，状态和备注是否矛盾。
- 独立接口文档与 vault 的接口段是否一致。
- 删除、移动或重命名后的路径是否仍被引用。
- “待确认”内容是否被其他文档误写成既定事实。

### 2.2 文档与源码

- 文档列出的模块、入口、接口和实体是否真实存在。
- 源码新增的关键公开能力是否缺少对应文档。
- 模块职责和依赖方向是否与实现一致。
- 标记完成的任务是否有对应产出；文件存在不能单独证明功能完成。
- ID、时间、错误、日志、分页等实现是否遵循项目约定。

### 2.3 接口与数据契约

- 路径、方法、参数、返回、错误响应、认证和权限。
- DTO/schema 字段、类型、可空性、默认值和分页格式。
- 实体字段、关系、索引、唯一约束、枚举和迁移。
- 公开契约在 docs、vault、源码和测试之间是否一致。

### 2.4 配置与清单

- `.env.example` 是否覆盖代码实际读取的环境变量。
- 文档声明的变量是否已弃用或未使用。
- 启动命令、默认端口和构建脚本是否真实存在。
- 框架、运行时、数据库和关键依赖版本是否过期。

只报告变量名、用途和位置，禁止输出秘密值。

### 2.5 测试与进度

- 测试是否引用旧接口、旧字段或已删除模块。
- 需求、版本路线和当前上线标准是否与任务状态和验收证据一致。
- 页面/路由/权限、页面状态、共享组件和视觉 token 是否与前端实现和前端 vault 一致。
- 测试期望是否与已确认需求冲突。
- vault 测试要点是否存在可识别的验证依据。
- 已完成任务是否缺少项目约定的验证证据。
- 待开发任务是否实际已有实现；Bug vault 四步记录是否与进度一致。

缺少测试只归为覆盖缺口，不直接认定实现错误。

## 三、分类与分级

固定分类：

- `DOC_STALE`：实现事实已变化，文档未同步。
- `CODE_DRIFT`：实现偏离已确认需求或设计。
- `STATUS_DRIFT`：开发进度、vault 与产出不符。
- `BROKEN_REFERENCE`：路径、编号或文档指针悬空。
- `CONTRACT_DRIFT`：接口、类型或数据契约漂移。
- `CONFIG_DRIFT`：依赖、脚本、环境或配置漂移。
- `VERSION_DRIFT`：版本路线、任务归属、上线阻断或验收证据漂移。
- `FRONTEND_DRIFT`：页面、路由、视觉基线或前端状态漂移。
- `AMBIGUOUS`：无法确定正确权威来源。
- `STYLE_ONLY`：仅格式或措辞问题，不影响事实一致性。

严重度和置信度必须分开：

| 维度 | 取值 |
|---|---|
| 严重度 | 阻断 / 高 / 中 / 低 |
| 置信度 | 已确认 / 高概率 / 待确认 |

每条发现使用会话内 ID `SYNC-001` 起，并至少包含：

- 文档证据（路径与位置）。
- 项目证据（源码、配置、清单或测试位置）。
- 冲突和可能影响。
- 建议权威来源与置信度。
- 推荐后续 skill。

`SYNC-*` 仅用于本次对话追踪，不要求创建文件。

## 五、后续路由

- 已确认只是文档、vault 或进度落后 → 《需求修改》按现状同步。
- 实现偏离既定需求且构成错误行为 → 《Bug修复》；仍须复现和定位。
- 实现属于尚未完成的明确任务 → 《项目开发》。
- 无法判断文档还是实现正确 → 《需求评估》。
- 架构或模块边界发生结构性偏离 → 《重构协调》。
- 只是发现代码结构可优化，不属于同步错误 → 《重构机会寻找》。

进入任何写操作前都必须让用户确认范围，并把 `SYNC-*` 摘要作为输入，避免重复全仓扫描。

## 完成标准

- [ ] 全程只读且未落盘报告。
- [ ] 每项确认的不一致都有文档与项目两侧证据。
- [ ] 路径和位置可复核，推断明确标注。
- [ ] 区分文档落后、实现偏离和无法判定。
- [ ] 严重度与置信度分开表达。
- [ ] 未泄露环境变量或配置秘密值。
- [ ] 报告包含已检查、未覆盖及限流降级情况。
- [ ] 后续路由能被对应 skill 直接接续。

---

## 反模式

- ❌ 检查时直接修正文档或代码。
- ❌ 把代码自动视为业务需求真相。
- ❌ 只列文件名，不给双侧证据。
- ❌ 把缺少测试直接认定为 Bug。
- ❌ 泄露 `.env`、token、密码或密钥值。
- ❌ 把格式和命名偏好升级为高风险同步错误。
- ❌ 429 后维持原并行量反复重试，或重复成功扫描域。
- ❌ 借同步检查扩展为全仓代码坏味道审查。


## 分支级证据边界

确认多人模式时可按用户指定的 base 和分支提供分支级文档、契约、测试与进度证据，并标明证据时点；这不授予 checkout、merge、rebase、push、删分支或任何写权限。功能冲突只列双方证据并交用户决定。
