# 最小上线标准评估（lite）

> 本 skill 是只读评估层，不改代码或项目文档，不安装依赖，不发布或部署。

## 触发与范围

- 初始拆分或现有项目中，有效可执行 `vault` 数量大于 3 时强制触发。
- 有效 vault 指包含实现目标、依赖、产出和测试要点的任务；归档、纯说明和存量档案不计入。
- 3 个及以下默认跳过，但用户可显式调用。
- 本规则不另设“大型项目”上限；数量很大时仍先给范围化评估，并明确 lite 流程的风险与边界。
- 初始化尚未落盘 vault 时，使用已确认的模块/功能草案计数，并标注为估算。

## 状态机

```text
COUNT → DEFINE_LAUNCH_OBJECTIVE → CLASSIFY_FEATURES
→ BUILD_FASTEST_PATH → CHECK_EXTENSIBILITY
→ USER_CONFIRM → HANDOFF
```

## 评估步骤

1. 读取 L1 项目备忘录、L2 需求与架构/开发进度、L3 vault 和依赖清单。
2. 统计有效任务、用户闭环、页面/接口能力组、外部集成、数据和横切约束。
3. 询问或复述最小上线目标：目标用户、核心闭环、支持平台、允许的已知限制和发布环境。
4. 将功能分为 `V0 最快上线`、`V1 完整体验`、`V2 扩展增长`，优先采用可独立验证的用户价值纵向切片。
5. 给出推荐最短路径，必要时给 1~2 个备选，并列出依赖、风险和验证方法。
6. 检查扩展性：稳定接口、数据迁移路径、模块边界、配置扩展点和兼容约束是否被保留。

不得为了速度延期认证、安全、权限、数据完整性、合规、最低可验证性或明确的核心用户闭环。扩展性不等于提前实现未来功能，也不要求为假设需求过度抽象。

## 就绪结论

后续复评固定使用：`READY`、`CONDITIONALLY READY`、`NOT READY`、`INSUFFICIENT EVIDENCE`。结论是 go/no-go 建议，不代表 merge、push、生产发布或部署许可。

## 反模式

- 用文件数量代替用户闭环分析。
- 通过延期安全、权限、数据完整性或测试制造“最快路径”。
- 把 V1/V2 的完成误记为 V0 完成。
- 没有证据却把未知写成通过。
- 在只读评估中直接改 docs、vault、代码或执行发布动作。
