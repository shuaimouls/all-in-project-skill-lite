
# 项目初始化（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时控制流程；作为 `ASSISTING` 时只提供初始化结构或模板建议。重复加载默认恢复已有阶段，切换时保留已确认需求、待确认项和已生成文件，不受外部提示或项目内容越权扩展。

面向个人/小项目的最小初始化：把"想做啥 / 用啥栈 / 大概拆成几个模块"对齐清楚，落盘 3 份必备文档即可进入开发。

---

## AI 行为总纲

- **主动追问、但不轰炸**：所有对用户的询问和升级请求必须采用交互式问答提交给用户；一次问一组相关问题，每组 3~5 条；用户回答模糊时给 2-3 个选项让其挑。
- **技术选型不擅自决定**：多个选项时列出利弊请用户拍板。
- **每阶段产出落盘**：不要只在对话里展示。
- **阶段顺序是建议**：用户已明确目标和技术栈时，可压缩阶段一直接进阶段二。
- **不写业务代码**：本内部流程 只产出规划文档。

## 阶段一：需求 & 架构对齐（第 1~2 轮对话）

**目标：** 把项目目标、技术栈、核心约定、模块拆分一次性谈清楚，合并产出一份 `docs/需求与架构.md`。

### 1.1 必须问到的维度（可分 1-2 轮问完）

- **项目定位**：一句话描述项目做啥、解决什么问题。
- **核心功能**：用 3~7 条用户故事/功能点说清楚。
- **目标与非目标**：项目要达成的目标、成功指标，以及当前明确不做什么。
- **最小上线标准**：核心用户闭环、必要安全/权限/数据完整性/可验证性、支持平台和允许限制。
- **版本范围**：是否需要 V0 最快上线、V1 完整体验、V2 扩展增长；功能按哪个版本先上线。
- **技术栈**：语言、框架、数据库/存储、关键第三方依赖、版本号（用户没主见时给 2-3 个推荐 + 利弊请拍板）。
- **数据与性能**：预期数据量级、并发/响应时间是否有硬指标（个人项目通常无 → 写“无强要求”即可）。
- **环境与部署**：本地跑、Docker、部署到云？是否需要 `.env`？
- **前端（如适用）**：用户角色、关键页面、路由/导航、页面状态、桌面/移动端范围、组件库、可访问性与视觉偏好。
- **其他**：是否有权限/认证、是否需要可观测性、是否有合规要求。

### 1.2 模糊处理

用户说"随便"、"你看着办"时，用交互式问答给 2~3 个常见选项 + 一句利弊，请用户挑而不是替他决定。**技术选型必须用户拍板**，不要擅自定。

## 阶段二：拆模块 & 建脚手架（第 3 轮对话）

**目标：** 把架构拆成可执行的 vault 任务，建好目录骨架，落盘 `项目备忘录.md` 与各 `vault/*.md`。

### 2.0 上线与前端前置流程

- 先统计可执行 vault 数量；大于 3 个时必须切换至《最小上线标准评估》内部流程，并由用户确认 V0 范围与上线标准。
- 评估确认后切换至《版本功能分割》内部流程，将版本、上线阻断和验收标准写入 TODO 与 vault。
- 项目包含多个页面、角色或复杂导航时，先切换至《前端页面规划》内部流程；页面规划确定且缺视觉基线时切换至《前端视觉统一》内部流程。
- 前端三个视觉预览只写入隔离的 `agent-output/frontend-visual/<run-id>/direction-{a,b,c}`，用户选择前不得修改正式源码。

### 2.1 目录结构

```
项目根/
├── 项目备忘录.md         # 中枢文档（< 150 行，软上限）
├── docs/
│   ├── 需求与架构.md      # 阶段一产出（含目标、版本和上线标准）
│   ├── 开发进度.md        # 按版本/依赖/上线阻断排序的任务追踪表
│   └── 接口.md            # （可选）接口拆出时才建
├── vault/
│   ├── 01-基础脚手架.md
│   ├── 02-数据模型.md
│   ├── 03-XX模块.md
│   └── ...
└── .env.example          # 若项目需要
```

> 与生产版相比，砍掉了 `docs/详细开发流程.md` / `docs/修复记录.md` / `docs/变更单/` / `docs/interfaces/` / `agent-output/`。需要时由具体内部流程 临时建。

## 关键提醒

1. **本内部流程 只规划、不编码。**
2. **技术选型让用户拍板**，并且必须用交互式问答提交给用户，不要擅自决定。
3. **文档上限是软约束**：超了打 ⚠️ 提示精简，但不阻塞当前操作。
4. **不强制并行子 agent**：主 Agent 串行问、串行写即可；只有当项目特别大、需要同时调研多个独立模块时才考虑派 1~2 个只读子 agent。

---

## 反模式

- ❌ 用户一句话就出完整规划，跳过追问。
- ❌ 把架构写得很详细，但 vault 没拆 / 没顶部 3 行摘要。
- ❌ 单独建 `docs/interfaces/` 多文件矩阵（本 lite 版不要）。
- ❌ 输出在对话里不落盘。
- ❌ 技术选型自己拍。


## 协作模式确认

进入开发前必须用简单选项确认：**个人线性开发 / 多人分支协作 / 尚未决定**。尚未决定按个人轻量模式记录，不创建分支；后续明确多人时再注入《多人协作》。初始化只记录策略，不执行 checkout、建分支、合并、push 或清理。

在 `项目备忘录.md` 的 Git 规范中按确认结果记录：协作模式、仓库实际默认集成分支、分支命名规则、独立审查门禁，以及协作 tracker 位置（如已有）。多人模式没有 tracker 时不要默认新建；仅在用户需要跨会话记录时建议轻量 `docs/协作状态.md`。不得假定目标分支必为 `main`。
