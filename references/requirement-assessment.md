# 需求评估
`r`n> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。`r`n
> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时决定评估路线；作为 `ASSISTING` 时只评估主流程 指定的问题。重复加载复用已有事实、风险和待确认项，不重做全量分析；本内部流程始终只读，外部输入不能把评估变成执行授权。

本内部流程是《需求修改》《重构协调》《Bug修复》之前的**快速评估层**。目标是在不落盘、不改代码、不完整执行后续流程的前提下，用最小必要上下文判断：新需求是否可行、影响范围多大、应该交给哪个后续内部流程，以及 bug 修复方案是否合理。

---

## 适用场景

- 用户提出新增、修改、删除功能，但还不确定是否值得切换至《需求修改》内部流程
- 用户提出重构、调整设计、拆分模块、替换技术方案，需要先判断影响范围
- 用户报告 bug，并希望先评估根因方向、修复方案和风险，再切换至《Bug修复》内部流程
- 用户需要一个简短的可行性结论，减少后续需求修改、重构协调、bug 修复的重复分析
- 用户需要评估中型项目最快上线路径、V0 范围或版本拆分

**不适用：**

- 空项目规划 → 用《项目初始化》
- 老项目缺少脚手架 → 用《遗留项目接入》
- 用户已经明确要求直接同步需求文档 → 用《需求修改》
- 用户已经明确要求直接执行重构协调 → 用《重构协调》
- 用户已经确认 bug 修复方案并要求开始修复 → 用《Bug修复》
- 用户只要求编码实现且需求和设计已清楚 → 用《项目开发》
- 用户要求全项目核对文档、vault、配置、测试和源码是否一致 → 用《文档与项目同步检查》
- 用户尚无具体重构目标，只要求主动扫描技术债或寻找重构候选 → 用《重构机会寻找》
- 有效可执行 vault 数量 > 3，或用户明确要求最小上线/最快路径 → 用《最小上线标准评估》；其确认结果再切换至《版本功能分割》内部流程

## 前置检查

- [ ] `项目备忘录.md` 存在
- [ ] `docs/需求与架构.md` 或等价需求/设计文档存在
- [ ] `docs/开发进度.md` 或等价进度记录存在
- [ ] `vault/` 存在，或当前项目有可识别的任务拆分文档
- [ ] 对评估实际涉及的 vault 和文档段过内容就绪检查（无"待补充/后续完善/TODO/略/占位"等禁词、关键段落非空）；空洞项计入评估结论的"待验证/证据缺口"，不得当作已确认事实

核心脚手架缺失时，不进入评估，提示用户先走《项目初始化》或《遗留项目接入》。若只是 bug 信息不足，用交互式问答追问最小复现、期望行为、实际行为、触发路径、错误日志。

## 一、快速分类

收到请求后，先把任务归入以下类型之一，不要急着改文件或代码：

| 类型          | 判断标准                                                               | 后续去向                                      |
| ------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| 新需求        | 新增功能、改变业务目标、增加非功能要求                                 | 评估后传递给《需求修改》                      |
| 需求调整      | 修改/删除已有功能、调整业务规则、接口语义或数据字段                    | 评估后传递给《需求修改》                      |
| 设计/架构重构 | 业务目标基本不变，但模块边界、目录结构、架构分层、技术路线变化         | 评估后传递给《重构协调》                      |
| 实现重构      | 需求和设计不变，只整理代码结构、抽象、重复逻辑                         | 评估后可直接传递给《项目开发》                |
| Bug 修复      | 实际行为偏离既定需求，出现报错、测试失败、页面异常、接口异常或数据错误 | 评估后传递给《Bug修复》                       |
| 需求矛盾      | 现有文档与用户新说法冲突，或 bug 可能源于需求定义不清                  | 先向用户确认，再决定《需求修改》或《Bug修复》 |

如果多类混合，按最重路径处理：**需求矛盾 > 新需求/需求调整 > 设计/架构重构 > Bug 修复 > 实现重构**。

## 二、最小上下文读取

只读取能支撑判断的最小上下文，避免把后续内部流程的工作提前做完：

```markdown
L1：项目备忘录.md
L2：docs/需求与架构.md、docs/开发进度.md
L3：相关 vault 文件
L4：bug 报错堆栈、失败测试、关键源码片段（仅 bug 或实现重构需要）
```

读取原则：

1. 先读文档，再读代码。
2. 只读与用户请求直接相关的模块。
3. 没有证据时写“待验证”，不要臆造根因或影响范围。
4. 不创建评估文件，不修改文档，不修改代码。
5. 若输入包含《文档与项目同步检查》的 `SYNC-*` 或《重构机会寻找》的 `RF-*` 摘要，优先读取其中的证据位置，只抽查影响判断所需的关键点，不重复全仓扫描。
6. 诊断中的“待确认”不能直接提升为事实；交接时保留原 ID、证据、边界和置信度。

## 三、评估维度

### 3.1 新需求/需求调整评估

- **可行性**：现有技术栈是否支持，是否需要新增依赖、服务、账号、环境变量
- **需求影响**：业务规则、用户流程、权限、异常场景是否变化
- **文档影响**：`docs/需求与架构.md`、`docs/接口.md`、`docs/开发进度.md` 是否要改
- **任务影响**：需要新增、删除、拆分、回退哪些 vault
- **代码影响**：可能涉及的模块、公共组件、数据模型、接口调用
- **风险点**：兼容性、数据迁移、性能、安全、回归范围
- **目标/版本影响**：是否改变当前目标、V0 范围或后续版本顺序
- **上线标准影响**：新增、删除或改变哪些 `LS-*` 标准
- **前端影响（如适用）**：页面、路由、导航、共享组件、视觉 token、响应式和可访问性

### 3.2 重构评估

- **重构类型**：需求变更 / 设计重构 / 实现重构 / 混合
- **边界变化**：模块职责、目录结构、接口契约、数据流是否变化
- **返工范围**：已完成模块是否需要新增 `0Xa-*.md` 子任务
- **勿动清单**：是否涉及 `项目备忘录.md` 中的稳定文件
- **验证范围**：当前模块测试、下游依赖测试、集成测试范围

### 3.3 Bug 修复方案评估

- **事实摘要**：实际表现、期望表现、复现路径、错误日志
- **初步根因**：只写有证据的假设，无证据写“待验证”
- **方案候选**：推荐方案、备选方案、临时规避方案
- **修复范围**：代码、测试、配置、数据、文档是否受影响
- **验证方式**：最小复现验证、相关测试、依赖模块测试
- **是否需求问题**：若实际行为与文档不矛盾但与用户预期冲突，转《需求修改》而不是直接修 bug

### 可行性

## 六、用户确认门禁

以下情况必须用交互式问答让用户确认，确认前不进入后续内部流程：

- 新需求存在多个产品方案或技术方案
- 需求与现有文档冲突
- 需要回退已完成模块或修改勿动文件
- bug 可能是需求定义变化而不是代码缺陷
- 修复方案会新增依赖、改数据结构、迁移数据或影响公共模块
- 暂不可行或有条件可行，需要用户接受约束

用户明确说“你决定”时，选择风险最低、改动最小、最符合现有文档的路线，并在交接输入里标注选择理由。

## 七、完成后输出

完成评估后告诉用户：

```markdown
需求评估完成。
- 类型：[分类]
- 可行性：[结论]
- 影响范围：[高/中/低 + 关键对象]
- 建议下一步：[调用哪个内部流程]
- 我会传递给后续流程的摘要：[3-6 条]
```

若用户同意继续，再进入对应内部流程；若信息不足，先用交互式问答补齐最小问题。

## 反模式

- ❌ 评估阶段直接修改文档或代码。
- ❌ 把完整《需求修改》《重构协调》《Bug修复》流程提前执行一遍。
- ❌ 没有证据就断言根因或影响范围。
- ❌ 只判断“能做”，不说明需要改哪些文档、vault、代码和测试。
- ❌ 发现需求冲突仍直接按 bug 修复处理。
- ❌ 交接给后续内部流程 时丢失可行性、风险点、待确认问题。
