
# Goal 监工（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 本内部流程是目标级控制面，不是执行 Agent。它只在用户明确启动并完成一次授权确认后运行；第 0 层主 Agent 保持最短上下文并负责调度、验收和升级，实际读取、实现、测试与局部诊断必须委派给第 1/2 层子 Agent。任何时刻仍只有一个生命周期流程为 `ACTIVE`。

## 适用场景

- `项目备忘录.md`、`docs/需求与架构.md`、`docs/开发进度.md` 和可执行 `vault/` 已就位。
- 用户明确要求“监工目标”“自动推进到完成”或“持续完成当前版本”。
- 规划文档**通过 PREFLIGHT 就绪检查**（见状态机第一节），目标、非目标、当前目标版本和完成定义均为真实内容而非骨架。

规划不完整、目标冲突或 vault 无法执行时，先转《项目初始化》《遗留项目接入》《需求修改》或《最小上线标准评估》。

## PREFLIGHT 就绪检查（进入 GOAL_CONFIRMED 前必须全部通过）

- [ ] `docs/需求与架构.md` 的目标表、版本路线表、最小上线标准表各有 ≥1 行真实数据，无禁词（待补充 / 后续完善 / TODO / TBD / 略 / 占位 / 模板残留）
- [ ] 当前版本范围内每个 vault 通过内容就绪检查：「接口与类型」「实现要点」（≥3 条具体项）「测试要点」（≥1 条具体场景）「产出清单」（路径非占位名）四段填实
- [ ] `docs/开发进度.md` 中当前版本任务的"验收/证据"列非空洞（待开发项可为"待验证"，但不得为禁词）

任一失败 → **不启动 Goal**，列出缺口清单，转《项目初始化》或《需求修改》补全；Goal 模式文档空洞的返工成本是三层委派倍增，此处必须拦截。

## 启动合同

启动时只询问一次，逐项记录动作、精确对象、范围和是否允许自动执行：

| 动作 | 授权范围 |
|---|---|
| 文档/代码/测试写入 | 指定项目目录、文件或当前任务 |
| 安装依赖/联网下载 | 指定包、来源和用途 |
| 测试/构建/开发服务 | 指定命令或项目脚本 |
| 本地 commit | 指定分支和当前 Goal 任务 |
| 建立/切换分支 | 指定分支名和用途 |
| 本地 merge | 指定源、目标和策略 |
| push | 指定 remote 和 branch |
| 部署 | 仅限项目已有且已记录的部署命令/环境 |
| 删除临时文件/预览 | 指定目录和条件 |
| 删除文件/分支/数据迁移 | 必须逐项、逐对象说明 |
| 审查深度 | 指定各任务审查级别（L0/L1/L2）或授权监工按《代码审查》§二之二分级规则自动定级；L2 对象必须逐项列出 |

未勾选动作不可执行。`force push`、`reset --hard`、rebase 或其他历史改写不纳入通用 Goal 授权；生产部署不因本内部流程 自动获得能力。授权不可扩展到新目标、新版本、新分支、新远端环境或未列出的外部系统。

**范围泛化**：授权对象以目录或路径模式（如 `src/auth/`、`vault/*.md`、`docs/`）给出时，该范围内新建、修改、删除文件均视为合同内，不因出现合同未逐一点名的新文件而升级。只有超出已授权目录/模式、或触及上表未勾选的动作类型时才算超合同。

一次性授权不替代产品或技术决策。新技术栈/依赖、公共 API/类型、数据迁移语义、权限安全、合规、许可证冲突和需求矛盾仍按「升级分级」处理：阻断级立即升级，决策级记入待确认队列按检查点批量确认。

## 最短上下文与三层委派

Goal 模式固定使用以下运行时结构：

```text
第 0 层：Goal 主 Agent（调度、合同、进度索引、验收、升级）
├── 第 1 层执行 Agent A（一个 ready 任务或一个独立工作域）
│   └── 第 2 层局部 Agent A1（可选，一个精确子问题）
└── 第 1 层执行 Agent B（可选，互不冲突的 ready 任务或工作域）
    └── 第 2 层局部 Agent B1（可选，一个精确子问题）
```

- 第 0 层同时最多委派 2 个第 1 层 Agent；每个第 1 层同时最多委派 1 个第 2 层 Agent；第 2 层禁止继续委派。满载时含主 Agent 共最多 5 个 Agent。
- 两个并发的第 1 层工作单元必须归属同一个 `ACTIVE` 生命周期流程，并且依赖独立、读写范围不重叠或已隔离；需要不同生命周期流程的 ready 任务必须串行切换。`唯一 ACTIVE 流程` 约束流程控制权，Agent 数量另受上述上限约束。
- 不限制 ready 任务的子 Agent 调用次数，不设置总调用预算。排队、重试、替换和新会话均不得绕过层级及同时委派上限。
- 第 0 层常驻内容只包括：Goal 与完成定义、授权/禁止项、ready/blocked/completed 索引、决策级待确认队列、Agent 占用情况、证据指针和下一动作。源码、长日志、完整文档及历史对话不进入常驻上下文。
- 每次委派使用最小任务包：任务 ID 与完成定义、精确读写范围、2–5 个入口文件、依赖/禁止项、允许动作、验证命令和证据指针。第 1 层委派第 2 层时再次裁剪，不得透传自己的完整上下文。
- 任务包必须附带「升级代理规则」：子 Agent 在 Goal 模式下**不沿用**被委派内部流程（如《项目开发》《Bug修复》）自带的升级门禁，仅以下事项需要向上报告——需求/文档/公共 API 矛盾且无法本地裁决、必须触碰合同外动作、安全/权限/数据迁移语义变化、同一问题两次修复失败。其余一切按「可自主解决事项」自行决定，并写入返回压缩包的「关键决策」字段。子 Agent 不得直接向用户提问；拿不准的事项按决策级记入「关键决策」并继续，由第 0 层汇总进待确认队列。
- 每层返回固定压缩包：状态、改动文件、关键决策（含自主决定事项与待背书事项）、验证命令与结果摘要、证据指针、未完成/阻断、下一动作。原始输出留在文件或工具结果中；上层仅按指针抽查，不重复全量读取。
- 第 1 层负责当前任务的实际工作和端到端结果；第 2 层只处理可独立验收的局部检索、实现、测试或验证，不接管 Goal 调度或用户决策。

## 可自主解决事项（不升级）

以下事项由执行层自行决定并记入该任务的「决策日志」（子 Agent 压缩包的「关键决策」字段），**不构成语义冲突，不转 WAITING_USER，不触发任何用户询问**：

- 命名（变量、函数、文件、内部组件、CSS 类），以及文件/目录内部组织方式
- 非公共 API 的内部实现选择：算法、库内工具函数、私有类型、模块内分层
- 测试写法、用例数量与组织、测试数据构造、断言风格
- 文档措辞、注释、格式排版、vault 内「实现要点」的表达顺序
- 合同范围内的等价重构：抽函数、改名、移动私有代码、消除重复
- 错误处理与日志的局部形式（在不改变对外行为契约的前提下）
- UI 文案、按钮/标签文字、默认值、占位文本（已确认视觉基线内的样式微调同理）
- 依赖的补丁/次版本选择（在已授权安装该依赖的前提下）

判断原则：不改变外部可观察行为、不改公共契约、不碰安全/权限/数据语义、不超出合同范围的内部决定，一律自主。只有「这个决定会让另一个已确认事实（文档、公共 API、需求）变错」时，才可能进入升级分级。

## 升级分级

Goal 模式下，需要用户输入的事项分两级处理：

| 级别 | 触发条件 | 处理方式 |
|---|---|---|
| **阻断级** | 没有该决定就无法继续任何 ready 任务：需求/文档/公共 API 互相矛盾且双方都可能是权威来源；必须触碰合同外动作才能推进；安全/权限/数据迁移/合规语义变化；同一问题两次修复仍失败 | 立即停止当前线，用「完全阻断升级包」一次问清；等待期间继续推进其他不依赖该决定的 ready 任务 |
| **决策级** | 有合理默认、可继续推进、但属于产品/技术取舍需要用户事后背书：默认值的选取、UI 文案风格、非阻断性的技术选型分叉、合同内等价方案之间的取舍 | 第 0 层按推荐方案继续推进，同时把事项记入「待确认队列」，**不打断执行** |

决策级队列在以下检查点用**一次** `AskUserQuestion` 批量提交（单次最多 4 问，超过 4 条按优先级截取，其余顺延下一检查点）：

1. 任一工作单元验收完成时（队列非空才问）
2. 当前版本收尾前（队列必须清空）
3. 真正阻断、需要用户输入时（顺带批量问）

用户否决某条决策级事项时，按用户意见返工该条；其余已推进工作不受影响。决策级事项不阻塞 `COMPLETED` 判定之外的任何中间状态；版本收尾前队列清空是 `COMPLETED` 的必要条件。

## 状态机

```text
PREFLIGHT
  → GOAL_CONFIRMED
  → SELECT_NEXT
  → DELEGATE
  → VERIFY
  → SELECT_NEXT
  → COMPLETED

任一阶段可转 BLOCKED；阻断级事项转 WAITING_USER，决策级事项入待确认队列不打断。
```

## 自动推进循环

1. 第 0 层只读取目标版本、完成定义、禁止项、授权合同、进度索引和现有证据指针。
2. 计算 ready 任务：依赖已完成、范围明确、授权覆盖、无未决语义冲突。
3. 选择顺序：当前版本上线阻断任务 → 当前版本普通任务 → 后续版本中不阻塞当前目标的独立任务。
4. 选择下一个 `ACTIVE` 生命周期流程，再从其可处理的 ready 集合中选择最多 2 个依赖独立且读写范围不冲突的工作单元；跨 生命周期流程、存在依赖、共享写入或证据不足时只选 1 个。
5. 将唯一 `ACTIVE` 生命周期职责交给对应内部流程，并由第 1 层执行 Agent 实际完成工作单元：实现切换至《项目开发》内部流程，行为缺陷切换至《Bug修复》内部流程，需求变化切换至《需求修改》内部流程，前端决策交前端内部流程，审查/合并遵循独立门禁。
6. 第 1 层需要进一步压缩上下文时，同时只能委派 1 个边界明确的第 2 层局部 Agent；该 Agent 返回并释放槽位后可继续调用其他第 2 层 Agent。第 1 层负责最终集成、测试和任务级自审。
7. 第 0 层接收压缩交接：状态、改动文件、关键决策、测试/验收摘要、证据指针、未完成/阻断和下一动作；只抽查完成条件所需证据。交接中的自主决策直接采信；标记为待背书的事项并入决策级待确认队列。
8. 验证目标完成条件后更新 completed/blocked/ready 索引，释放对应 Agent 槽位。待确认队列非空时，按「升级分级」的检查点规则用一次 `AskUserQuestion` 批量提交；为空则不询问，直接继续或结束。

Goal 在委派期间是 `COORDINATING/ASSISTING`，不能用自身身份扩大执行流程的权限。第 0 层除调度所需的索引读取和完成条件证据抽查外，不得承担源码读取、编码、测试执行、日志分析或局部诊断。

## 阻断处理

“优先绕过”只允许：更换等价工具、使用本地资产替代不可达网络、降低并行量、替换中断 Agent、重排无依赖任务、提前做后续版本独立基础任务。不得降低验收标准，不得改测试迁就实现，不得跳过安全、权限、数据完整性、必要测试、用户决策或审查门禁。

当前任务阻断时：

- 先尝试一次已授权、需求等价、可验证、非破坏性的替代路线。
- 没有替代路线时保留阻断原因，继续寻找任何版本的 ready 任务。
- 跨版本执行时保持原任务版本归属；后续任务不能计入当前版本完成。
- 同一问题修复两次仍失败，按阻断级升级处理（用完全阻断升级包一次问清），不再循环。

完全阻断是指：没有同时满足依赖、授权、需求等价和可验证条件的 ready 任务，且 Goal 完成条件未满足。

## 完成标准

只有同时满足以下条件才标记 `COMPLETED`：

- 当前 Goal 所需版本的必需任务均完成；
- 版本范围内的验收标准、测试均有当前证据；**每个工作单元只要求一层有效审查结论**（自审 `L0-SKIP`、简化 L1 或完整 L2），第 0 层按证据指针抽查，不对同一产出重复执行完整审查；
- 决策级待确认队列已清空（全部经用户背书或否决后返工完成）；
- 没有阻断级 finding 或未决产品/技术冲突；
- `docs/开发进度.md` 已更新至最新状态，且本轮接口变化已回写对应 vault「接口与类型」；
- merge、push、部署是否属于完成条件，按启动合同逐项判断。

## 反模式

- 把一次授权解释成未列出的全仓、全版本或全外部系统授权。
- 第 0 层持续深读源码、亲自编码或吸收完整日志，使 Goal 主上下文演变为执行上下文。
- 把整段会话、全量 docs/vault 或子 Agent 原始输出逐层转发。
- 第 0 层同时委派超过 2 个第 1 层 Agent、第 1 层同时委派超过 1 个第 2 层 Agent，或允许第 2 层继续委派。
- 用排队、重试、替换或新会话掩盖超层级、超并发；不限制累计调用次数不等于允许无限同时扇出。
- 并行处理存在依赖或写入范围重叠的任务。
- 为了“自动完成”跳过安全、测试、审查、需求确认或数据迁移门禁。
- 把应定 L2 的契约/安全改动降级为 L0/L1 以绕过完整审查。
- 把后续版本任务算作当前版本已完成。
- 自己替代《项目开发》《Bug修复》《代码审查》作专业判断。
- 遇到局部阻断就停下，或无限重复同一失败路线。
- 把「可自主解决事项」清单内的命名、内部实现、文案等逐级上报，用决策级队列当借口频繁打断用户。
- 决策级队列攒着不问，或每条单独发一次 `AskUserQuestion`，退化为逐条打断。
- 子 Agent 绕过第 0 层直接向用户提问，或把被委派流程的独立门禁原样带进 Goal 重复询问。
