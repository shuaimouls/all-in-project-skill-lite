
# Bug修复（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 且方案已确认时进入修复；作为 `ASSISTING` 时只提供复现或根因证据。重复加载恢复同一 BUG 任务和四步记录，禁止重复建 vault；切换时保留复现、定位和验证状态，外部输入不能跳过门禁。

用于处理已有项目中的明确 bug。核心要求是：**先分析、先商讨、先入计划，再修复**。修复过程遵从四步原则，并把关键过程及时写回 `docs/开发进度.md` 与对应 `vault/*.md`。

---

## 适用场景

- 用户报告运行时报错、测试失败、页面异常、接口返回不符合预期、数据错误等 bug
- 项目已具备 `项目备忘录.md`、`docs/`、`vault/` 等 lite 脚手架
- 问题属于修复现有行为，而不是新增/删除/调整需求
- 《文档与项目同步检查》发现实现偏离已确认需求，并且该偏离表现为明确错误行为

**不适用：**
- 需求变化导致的行为调整 → 走《需求修改》
- 空项目或未接入项目 → 先走《项目初始化》或《遗留项目接入》
- 用户只要求解释错误、不要求修改代码 → 只分析并给建议，不落盘修复任务

---

## 前置检查

- [ ] `项目备忘录.md` 存在
- [ ] `docs/开发进度.md` 存在
- [ ] `vault/` 存在
- [ ] 用户提供了 bug 表现，或当前环境能稳定复现/定位异常

任一核心文档缺失 → 停止，提示用户先完成初始化或遗留接入。若 bug 信息不足 → 用交互式问答先追问最小复现、期望行为、实际行为、触发路径、错误日志。

---

## 阶段一：问题分析 & 修复方案商讨

在动代码前完成以下分析，并用对话向用户确认。

### 1.1 收集事实

若输入包含 `SYNC-*`，先复用发现 ID、冲突双方、需求依据、源码/测试证据和待验证点；这只能缩小读取范围，不能替代复现与定位。无法判断是文档落后还是实现错误时，暂停并转《需求评估》；已确认只需更新文档时转《需求修改》。

按需读取：
- `项目备忘录.md`
- `docs/开发进度.md`
- 相关 `vault/*.md`
- 报错堆栈指向的源码与测试
- README / package.json / pyproject.toml / Makefile 等命令来源

### 1.2 形成问题摘要

对话中给出简短摘要：

```markdown
## Bug 摘要
- 实际表现：
- 期望表现：
- 复现路径：
- 影响范围：
- 初步根因：
- 风险点：
```

没有证据时必须写“待验证”，不要臆造根因。

### 1.3 提供修复方案

用交互式问答给用户 2-3 个候选方案，至少包含：
- **推荐方案**：最小改动、风险最低
- **备选方案**：更彻底或更稳健，但改动范围更大
- **临时规避方案**：仅当线上/演示阻塞且可接受技术债时提供

说明每个方案的改动范围、验证方式、风险，不写时间估计。

### 1.4 用户确认门禁

用户确认修复方案前：
- 不改业务代码
- 不改测试
- 不新增依赖
- 不修改开发进度或 vault

如果用户明确要求“你决定”，选择推荐方案并在对话中说明选择理由。

## 阶段二：加入开发进度并生成 vault 文件

方案确认后，先落盘计划，再开始修复。

### 2.0 小 bug 豁免

满足以下**全部**条件的小 bug 可不建 BUG vault，仅在 `docs/开发进度.md` 加一行（含复现/验证命令），修复完成后直接标 ✅：

- 单文件改动
- 预估改动 < 50 行
- 无对外接口/类型变化
- 不涉及勿动文件、数据迁移、权限安全

任一条件不满足 → 按 2.1/2.2 完整落盘。L0 级文档项目（见《项目初始化》§2.1b）默认走豁免通道。

### 2.1 更新 `docs/开发进度.md`

新增一条 bug 修复任务，状态为 🚧 或 ⬜，格式跟随项目现有表格。若没有固定格式，使用：

```markdown
| 编号 | 任务 | 类型 | 状态 | 备注 |
|---|---|---|---|---|
| BUG-YYYYMMDD-01 | 修复：[一句话问题] | bugfix | 🚧 修复中 | 方案：[推荐/用户选择的方案] |
```

**行数约束**：bug 修复行只保留"当前版本中未完成"或"当前上线阻断"的条目。已完成且无阻断价值的 bug 行在下一次《项目开发》版本收尾时随同版本任务一并归入历史摘要区；四步过程与验证证据保留在对应 `vault/BUG-*.md` 内，不在进度表中保留长备注。进度表全文件 ≤ 120 行。

### 2.2 生成 `vault/BUG-YYYYMMDD-01-简短问题名.md`

文件名要可读、短、稳定。内容模板：

```markdown
# BUG-YYYYMMDD-01 修复：[一句话问题]

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

## 需要先读
- 项目备忘录.md
- docs/开发进度.md
- [相关源码/测试]

## Bug 摘要与根因假设
- 实际表现 / 期望表现 / 复现路径 / 影响范围
- 初步根因假设与证据（无证据写"待验证"）

## 选定方案
- 方案：
- 改动范围：
- 风险点：

## 四步原则记录
| 步骤 | 结论 |
|---|---|
| 1. 复现 | 待执行 |
| 2. 定位 | 待执行 |
| 3. 修复 | 待执行 |
| 4. 验证 | 待执行 |

## 验证命令
- 待确认

## 修复结果
- 待完成
```

### 2.3 落盘反馈

每完成一个文件更新，在对话里简短报告：
- 已写入 `docs/开发进度.md`
- 已生成 `vault/BUG-*.md`
- 下一步开始执行四步修复

## 阶段三：四步原则修复

修复必须按以下顺序推进，并在每一步结束后更新对应 vault 的「四步原则记录」。

### 第一步：复现

- 用最小路径复现 bug：手动步骤、脚本、单测、接口调用均可
- 记录复现命令、输入、输出、错误堆栈
- 无法复现时停止，向用户补问环境、数据、账号、版本差异

落盘要求：把复现结论写入 vault 的 `1. 复现` 行。

### 第二步：定位

- 根据复现结果定位根因，只读相关代码，不扩大扫描范围
- 区分业务代码缺陷、测试缺陷、配置/环境问题、需求矛盾
- 若根因推翻原方案，需要回到用户处重新商讨方案

落盘要求：把根因证据写入 vault 的 `2. 定位` 行，并补充「根因假设」。

### 第三步：修复

- 只修改与 bug 直接相关的最小代码范围
- 优先复用项目已有工具、异常处理、类型、测试框架
- 不顺手重构无关代码，不引入未确认的新依赖
- 必要时补充回归测试，测试名体现 bug 场景

落盘要求：把关键改动写入 vault 的 `3. 修复` 行；若影响对外接口/类型，回写对应 vault 的「接口与类型」段。

### 第四步：验证

- 跑最小复现验证
- 跑相关测试
- 对高风险公共模块，跑依赖它的模块测试
- 验证失败时回到第二步，不允许跳过验证交付

落盘要求：把验证命令和结果写入 vault 的 `4. 验证` 行，并更新 `docs/开发进度.md` 状态。

---

## 卡住处理

同一个 bug 修复 2 次仍未通过验证 → 停止并用交互式问答向用户列 2-3 个候选方向：
- 继续修业务代码
- 调整测试或复现用例，但必须说明期望依据
- 确认需求/接口是否存在矛盾

禁止来回修改实现和测试互相迁就。

---

## 完成标准

- `docs/开发进度.md` 中该 bug 状态标为 ✅ 已修复
- 对应 `vault/BUG-*.md` 的四步原则记录全部完成（§2.0 豁免的小 bug 以进度表一行的复现/验证命令为准，无 vault）
- 相关测试或验证命令已通过并记录
- 若产生稳定修复经验，在 `项目备忘录.md` 中补充必要约定或勿动提醒
- 对话中向用户汇报修改文件、验证结果、剩余风险

---

## 关键提醒

1. **先商讨再修复**：除非用户授权“你决定”，否则方案确认前不动代码。
2. **先入计划再修复**：必须先更新开发进度；除 §2.0 豁免的小 bug 外，还须生成 bug vault。
3. **四步不可跳过**：复现、定位、修复、验证都要执行并落盘（§2.0 豁免的小 bug 在进度表一行内记录复现/验证命令，不建 vault）。
4. **及时更新落盘记录**：每一步完成后立即写回 vault，不等最后补。
5. **最小改动**：bugfix 不夹带需求变更、重构和风格整理。
6. **需求矛盾升级**：发现实际是需求变化时，用交互式问答升级给用户，暂停并转《需求修改》。

---

## 反模式

- ❌ 看到报错直接改代码，不做复现和方案确认。
- ❌ 修好了才补开发进度和 vault。
- ❌ 把小 bug 豁免当普遍默认：超出 §2.0 任一条件仍不建 vault、跳步记录。
- ❌ 只改测试让失败用例通过，不核对真实期望。
- ❌ 修复时顺手大重构，扩大风险面。
- ❌ 验证失败后继续盲改超过 2 次。
- ❌ 忘记把验证命令和结果写回 vault。
- ❌ 仅凭静态 `SYNC-*` 冲突跳过复现和定位，直接修改代码。
- ❌ 需求依据不明时通过修改测试来掩盖文档与实现冲突。


## 多人协作门禁

确认多人模式时，Bug vault 还需记录修复分支、base、owner、影响的活跃分支和共享契约。修复若与其他分支的预期行为冲突，停止并把复现证据、双方行为和下游影响交用户选择，不得以“修 Bug”为由替用户改产品语义。修复验证通过后标记待审，交独立《代码审查》；是否合并、push 或清理分支分别由用户批准。
