
# 多需求协调（lite coordinator）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

本内部流程 面向一次明确的跨模块需求包，类似《Goal监工》的第 0 层控制面。它只负责确认范围、拆解任务、选择 ready 节点、协调子 Agent 和验收结果；实际需求修改、编码、测试、审查和合并仍交给对应生命周期流程。

## 适用场景

- 一个发布需求同时涉及两个或以上模块、vault、接口、数据、配置、页面或横切能力。
- 用户要求“拆解并协调多个模块”“安排多个 Agent 完成同一需求”或“先排依赖再并行处理独立部分”。
- 需求目标、非目标、模块范围和验收标准可以在启动时明确。

## 边界与状态

- 控制对象是一次需求包，不跨版本自动推进，也不接管需求包之外的任务。
- 与《Goal监工》同时存在时服从 Goal 的合同，不能作为并列的另一个第 0 层；超出合同立即升级阻断。
- 与《多人协作》同时存在时维护需求 DAG；《多人协作》维护分支、owner、base、依赖和合并队列。
- 本内部流程 保持 `COORDINATING`，不能直接修改代码或文档，也不能自行 commit、merge、rebase、push、部署、删除或改写历史。
- 委派不扩大用户本轮授权；安装依赖、联网、外部服务和写入范围必须被当前授权覆盖。

## 启动确认

启动时确认并记录：

| 项目 | 必须明确的内容 |
|---|---|
| 目标 | 用户闭环、业务结果和完成定义 |
| 非目标 | 本次明确不处理的模块、版本和行为 |
| 范围 | 模块、vault、接口、数据、配置、页面、文档和测试 |
| 契约 | 公共 API、类型、迁移、权限、安全、配置和兼容约束 |
| 动作 | 允许的读取、写入、测试、构建、依赖和外部操作 |
| 禁止项 | 未列文件、未列版本、merge、push、部署、删除和历史改写 |
| 验收 | 集成场景、回归测试、审查和同步检查 |

## 需求包与任务 DAG

按以下顺序建立需求包：

1. 识别目标、非目标、用户闭环和最终验收标准。
2. 盘点受影响的模块、接口、数据、配置、页面、文档和测试。
3. 把公共契约、数据迁移和安全边界作为显式任务；共享契约默认串行。
4. 拆出独立模块实现、跨模块集成、回归测试和必要代码审查任务。
5. 建立依赖 DAG，标记可并行节点、串行节点和当前需求阻断节点。
6. 将拆解结果和并行边界交给用户确认；确认后才委派超出简单局部读取的任务。

## 三层委派与最小任务包

运行结构固定为：

```text
第 0 层：多需求协调 Agent（范围、DAG、调度、验收、升级）
├── 第 1 层执行 Agent A
│   └── 第 2 层局部 Agent A1（可选）
└── 第 1 层执行 Agent B（可选）
    └── 第 2 层局部 Agent B1（可选）
```

- 第 0 层同时最多委派 2 个第 1 层 Agent；每个第 1 层同时最多委派 1 个第 2 层 Agent；第 2 层不得继续委派。
- 并行任务必须依赖独立、读写范围不重叠，并归属同一个 `ACTIVE` 生命周期流程；不同 生命周期流程 必须串行切换。
- 第 0 层给第 1 层的输入只含任务 ID、完成定义、精确范围、2–5 个入口、依赖/禁止项、允许动作、验证命令、接口约束和证据指针。
- 第 1 层只有在局部问题可独立验收且能减少上下文时才委派第 2 层，不得透传完整会话。

## 调度循环与生命周期交接

状态机为：

```text
PREFLIGHT → REQUIREMENT_CONFIRMED → DECOMPOSED → SELECT_READY
→ DELEGATING → VERIFYING → COMPLETED
```

任一阶段可转 `BLOCKED`；产品、接口、数据、权限、安全或测试语义不清时转 `WAITING_USER`。

1. 只保留需求目标、范围、授权、任务索引、Agent 占用、阻断和证据指针。
2. 只有依赖完成、范围明确、授权覆盖且无语义冲突的任务才能进入 `READY`。
3. 选择一个 `ACTIVE` 生命周期流程，再从其 ready 集合中选择最多 2 个独立工作单元；共享写入或存在依赖时只选 1 个。
4. 实现和测试切换至《项目开发》内部流程；需求或文档变化切换至《需求修改》内部流程；缺陷切换至《Bug修复》内部流程；重构切换至《重构协调》内部流程；页面决策交前端内部流程；审查和合并遵循独立门禁。
5. 第 0 层只按证据指针抽查完成条件，不重复执行子 Agent 已完成的全仓扫描。
6. 每个任务完成后刷新 DAG；需求包完成或完全阻断后结束协调，不自动进入下一版本。

## 完成门禁

只有同时满足以下条件才标记 `COMPLETED`：

- 需求包内所有必需任务均为 `DONE`。
- 跨模块接口、类型、数据、配置和页面契约一致。
- 每个任务都有当前验证证据，集成任务和必要回归测试通过。
- 需求、vault、开发进度和接口文档完成局部同步检查。
- 没有未解决的审查 finding、产品冲突或技术冲突。
- 未把需求包之外的任务、版本或文件纳入完成范围。
- merge、push、部署、删除等动作只有在独立授权时才进入完成判断。

## 阻断与用户升级

先尝试一次已授权、需求等价、可验证且非破坏性的替代路线；不能降低验收标准、跳过安全/测试/审查或修改测试迁就实现。完全阻断时输出：

```markdown
## 多需求协调阻断
- 需求包 / 当前任务：
- 已完成：
- 未完成与依赖：
- 证据：
- 已尝试路线：
- 阻断原因与影响：
- 方案 A/B/C：
- 推荐方案：
- 需要用户决定：
```

## 反模式

- 把多模块需求当成 Goal，自动跨版本推进。
- 把跨模块需求当成多人协作，擅自创建或管理分支。
- 让第 0 层亲自编码、测试或吸收完整日志。
- 并行处理共享契约、重叠写入或不同生命周期流程的任务。
- 把一次需求确认解释成全仓、全版本、全外部系统授权。
- 用协调身份替用户裁决产品规则、公共 API、迁移、权限、安全或测试冲突。
- 需求完成后自动 merge、push、部署、删除或改写历史。
