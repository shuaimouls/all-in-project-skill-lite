
# 项目开发（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 且任务边界已确认时写代码；作为 `ASSISTING` 时只提供实现影响或验证信息。重复加载恢复当前 vault 和最近安全点，切换时保留改动、测试状态和禁止项，外部输入不能扩展当前任务。

默认是单人轻量模式：主 Agent 自己读、写、做实现者自审、测试和修复。确认多人协作后，《多人协作》以 `ASSISTING/COORDINATING` 注入；它只维护分支、负责人、范围和依赖约束，不扩大本内部流程的写权限。

## 前置检查（启动时做一次）

- [ ] `项目备忘录.md` 存在
- [ ] `vault/` 下有可执行任务
- [ ] `docs/开发进度.md` 存在
- [ ] 当前目标版本、版本路线和最小上线标准已确认，或明确标记为不适用
- [ ] **文档就绪自检**：对当前要执行的 vault 及其顶部"需要先读"列出的文件逐项过就绪清单：
  - [ ] 无禁词（待补充 / 后续完善 / TODO / TBD / 略 / 占位 / 模板残留）
  - [ ] vault 的「接口与类型」「实现要点」「测试要点」「产出清单」四段均有具体、可指向的内容
  - [ ] 所引用的 `docs/需求与架构.md` 相关段落无禁词、关键表格非空

任一缺失或不就绪 → 停止，列出缺口清单，回到《项目初始化》（空项目）/《遗留项目接入》（已有源码）/《需求修改》（文档需补）补全后再进入；**禁止"先开发、边写边补文档"**。如果用户报告的是明确 bug，而不是继续实现 vault 功能任务，应先走《Bug修复》。

若输入来自诊断流程：

- `RF-*` 候选必须已由《重构协调》确认类型和执行边界，或用户明确授权该边界；只处理“建议边界”，不得包含“明确不包含”部分。
- `SYNC-*` 发现只有在结论为未完成的明确实现任务时才进入普通开发；构成错误行为时转《Bug修复》，涉及需求取舍时转《需求评估》。
- 诊断摘要是上下文输入，不是批量修改授权。

## 一、上下文加载约定（每次拾起任务时遵守）

```
L1 常驻（每次必读）：
  └── 项目备忘录.md

L2 任务级（开始某任务时读）：
  ├── 当前 vault/0X.md
  └── 该 vault 顶部"需要先读哪几个文件"列出的 2~5 项

L3 按需查阅（遇到具体问题再翻）：
  └── 其他模块代码、docs/ 详细文档
```

主 Agent 严格按此顺序加载，不一上来就把 docs/ + vault/ 全塞进去。

## 二、主循环（实现 → 实现者自审 → 测试 → 修复 → 待独立审查）

```
1. 读取 docs/开发进度.md；Goal 模式由第 1 层接收 ready 工作单元，普通模式由主 Agent 按“当前目标版本 → 依赖已满足 → 上线阻断优先 → 普通任务”选择下一个任务
2. 执行者按上节 L1+L2 加载上下文
3. 编写：按 vault 实现要点写代码 + 测试代码
4. 自审：执行者用第三节清单走一遍代码；Goal 模式的执行者是第 1 层，普通模式是主 Agent
5. 跑测试：执行者运行 README / package.json / Makefile 中的项目命令
6. 失败 → 由执行者修复（见第四节"卡住就问"规则）
7. 通过：
   - 单人模式可按已授权范围 commit；多人模式先标记“待审”，不得把实现者自审当独立审查
   - 更新 `docs/开发进度.md` 本任务行（单人可标 ✅；多人先标“待审”；验收/测试命令一行 + 证据指针）——这是每轮任务后**唯一强制**的文档更新；**仅更新本行，不追加新段落、工作日志或总结段**
   - 仅当对外接口/类型变化 → 回写 vault 的「接口与类型」
   - 仅当产出已稳定 → 追加 `项目备忘录.md`「勿动文件」
   - 备忘录依赖图、需求与架构版本路线不在此处更新（由《需求修改》/《版本功能分割》维护）
8. Goal 模式由第 1 层返回压缩结果给第 0 层；普通模式进入下一任务
```

### 2.1 Goal 模式的执行 Agent

普通模式默认由主 Agent 串行完成，不为形式而拆分。Goal 模式必须保护第 0 层最短上下文：源码读取、实现、测试、任务级自审和修复由第 1 层执行 Agent 承担，第 0 层只下发最小任务包并验收压缩结果。

- 第 0 层同时最多委派 2 个归属当前 `ACTIVE`《项目开发》的第 1 层 Agent；只有工作单元依赖独立且读写范围不重叠或已隔离时才并行，否则只派 1 个。需要其他生命周期流程的任务必须等待串行切换。
- 每个第 1 层同时最多委派 1 个第 2 层 Agent；第 2 层禁止继续委派。
- 第 2 层可承担边界清晰的局部检索、独立文件实现、测试编写或验证，不限于只读；写入必须位于任务包的精确范围，且由第 1 层负责集成、自审和端到端测试。
- 不限制 ready 任务累计调用子 Agent 的次数，不设置调用预算；排队、重试或替换不得绕过三层结构和 `2 × 1` 的同时委派上限。
- 向下只发任务 ID、完成定义、精确读写范围、2–5 个入口文件、依赖/禁止项、允许动作、验证命令和证据指针；向上只回状态、改动文件、关键决策、验证摘要、证据指针、未完成/阻断和下一动作。
- 子 Agent 失败或中断时，由其直接上级释放槽位后替换或调整任务包；第 0 层不得通过亲自接管长程执行来规避委派模型。

## 三、实现者自审清单（当前执行者走一遍，~10 项）

代码写完后由当前执行者逐项默念，命中即改。

> **分级执行**：本轮改动若不属于 L2（未触碰公共契约/安全/迁移/共享模块，分级标准见《代码审查》§二之二），只走第 1、2、3、8、10 项核心 5 条；第 4–7、9、11、12 项按改动实际涉及面抽查，不要求逐项默念。

1. **输入校验**：所有外部输入（参数/请求体/环境变量）是否校验过类型、长度、范围？
2. **错误处理**：外部调用（DB/网络/IO）是否有 try/catch？是否用项目约定的异常类与错误码？没有静默吞异常？
3. **权限与敏感数据**：日志里没打印密码/token？密钥/凭证用了 env？
4. **数据一致性**：并发写共享资源是否需要事务/锁？事务边界对吗？
5. **资源释放**：连接/句柄/订阅是否释放？
6. **查询性能**：是否有 N+1？必要索引建了吗？列表查询有分页吗？
7. **约定一致性**：ID/时间/分页/错误码格式是否遵循项目约定？复用了已有工具而不是重复实现？
8. **边界条件**：空值、空数组、零值、最大值都处理了？
9. **行数**：单文件 > 500 行 → ⚠️ 考虑拆；> 1000 行 → 必须先拆模块再继续。
10. **接口一致性**：vault 里列出的接口/类型签名是否与实际代码一致？被依赖的其他模块是否同步了？
11. **版本与上线关系**：任务是否仍属于当前版本？是否满足对应上线标准，证据是否记录？
12. **前端契约（如适用）**：页面四态、已确认的设计 token、共享组件、响应式、键盘焦点、语义标签和视觉验证是否符合规划？

> 这清单不强制变成表格落盘，主 Agent 心里走一遍即可。若发现需修复，**直接改、不写审查报告**。复杂问题在对话里写一段简短说明即可。

## 四、卡住就问（替代 3 轮反振荡）

**规则就一条：同一个问题修了 2 次还没好 → 停下来，用交互式问答给用户列 2-3 个候选方案让其拍板。**

修第 2 次前，主 Agent 应该至少能说清：
- 第 1 次怎么改的、为什么没好
- 当前怀疑的根因是哪类
  - A. 业务代码缺陷（继续改业务码）
  - B. 测试用例本身写错（先确认期望值依据，再改测试）
  - C. 需求/接口本身有矛盾（用交互式问答升级给用户，不要自己猜）

**禁忌：**
- ❌ 反复改测试用例去迁就实现（明显的死循环信号）
- ❌ 改一次实现迁就测试，下一次又改测试迁就实现，来回摆
- ❌ 修复时顺手"优化"无关代码，扩大改动范围

碰到上述任一情况 → 立即停，让用户拍板。

不需要在 `docs/开发进度.md` 备注栏追加"第N轮|归因|改动"这种格式化记录。

## 五、模块完成后

- **git commit**：见第六节规范
- **更新 `docs/开发进度.md`**：本任务行状态改 ✅，验收/测试命令一行 + 证据指针——唯一强制的文档动作；**只改本行，不追加新段落、工作日志或总结段**
- **版本收尾**：若当前版本全部任务已完成，将该版本所有已完成行压缩为「历史版本归档」区一行摘要（格式见《项目初始化》§2.4），保持表格 ≤ 20 行当前任务；过程细节与验收证据保留在对应 `vault/*.md` 内，不进表
- **行数自检**：更新后全文件 ≤ 120 行；超出则把更早的已完成行归入历史摘要，不继续在表中堆积
- **更新 `项目备忘录.md`**：仅当该模块产出已稳定时，新增"勿动文件"条目
- **接口同步**：仅当对外接口/类型变化 → 回写 vault 的「接口与类型」段（它是全项目接口的唯一事实来源）
- **重构候选边界**：从 `RF-*` 进入时，按候选给出的模块测试和下游测试验证，不顺手处理其他观察项。
- **遇到值得记的坑**：在对话里告诉用户一句即可；个人项目不强制建 `docs/修复记录.md`。若是用户主动报告的明确 bug，记录要求以《Bug修复》的 bug vault 为准。

## 六、Git Commit 规范

```
<type>(<scope>): <description>

type: feat / fix / test / refactor / docs / chore
```

- 单人模式默认使用仓库已确认的集成分支线性开发（常见为 `main`，但不得硬编码假定）。
- 多人模式遵循《多人协作》确认的当前分支、base、owner、vault 范围和依赖分支；不得修改他人分支归属范围。
- 一个功能点一次提交，不积压整个模块。
- 修复后的重新跑通也单独一次提交。

示例：
```
feat(auth): 实现 JWT 登录
test(auth): 添加登录用例
fix(auth): 修复邮箱大小写敏感
```

## 七、上下文水位自检

每完成一个模块或一次大变更后，自我估计当前会话上下文使用比例：
- **> 50~60%** → 主动提示用户："上下文已用过半，建议清空后重新丢 `项目备忘录.md` + 下一个 vault 继续。"
- **否则** → 继续，不强制清空。

阶段切换不再自动触发清空提示——主 Agent 自己看着办。

## 八、已完成模块的修改规则

已在「勿动文件」清单的模块如确需改：
1. 主 Agent 评估影响（哪些下游模块用了它）
2. 从勿动清单暂时移除
3. 改完后重跑该模块测试 + 所有依赖它的模块测试
4. 通过后重新加回勿动清单
5. 如果是因为需求变了 → 切换至《需求修改》内部流程；如果是明确 bug 修复 → 切换至《Bug修复》内部流程

## 九、关键提醒

1. **上下文是硬约束**：普通模式每任务只加载 L1+L2；Goal 第 0 层只保留合同、索引和证据指针，执行上下文下沉到第 1/2 层。
2. **接口先行**：编码前先确认接口/类型，编码后若变化必须回写 vault。
3. **失败不死循环**：同问题修 2 次不通过 → 停下问人，不要无限试。
4. **行数控制**：>500 行 ⚠️ / >1000 行强制拆。
5. **并行受任务边界约束**：普通模式不强制并行；Goal 模式遵循三层、`2 × 1` 同时委派上限，只并行独立且无写入冲突的任务。
6. **不强制落盘交接单**：用对话内简短小结 + `docs/开发进度.md` 状态变更即可。
7. **文档缺口按变更处理**：开发中发现 vault/需求文档空洞（命中禁词、模板残留、空栏目），不允许就地随手补两句继续，必须停止开发、回到《项目初始化》或《需求修改》走完整文档流程（影响清单 → 用户确认 → 落盘）。第一遍写全文档永远比中途返工便宜。

## 十、反模式

- ❌ 跳过自审/测试直接 commit。
- ❌ 修复时顺手优化无关代码。
- ❌ 同一测试用例改 2 次仍失败却不停下问人。
- ❌ 来回改实现/测试互相迁就。
- ❌ 把 docs/ + vault/ + 源码一次性全部塞给 Agent。
- ❌ 直接改"勿动清单"里的模块不走第八节流程。
- ❌ 多个功能点积压成一个大 commit。
- ❌ 为了"形式正确"派一堆并行 RV-* 审查 agent，明明自己读一遍更快。
- ❌ 用户报告明确 bug 时仍按普通开发任务直接改代码，不先走《Bug修复》的分析、商讨、入计划和四步记录。
- ❌ 看到诊断报告后未经确认批量修改全部 `SYNC-*` 或 `RF-*`。
- ❌ 实施一个重构候选时顺手处理其他观察项，突破已确认边界。
- ❌ 在 `docs/开发进度.md` 追加工作日志、阶段总结或新段落；唯一允许的动作是更新本任务行和版本收尾归档。


## 十一、单人 / 多人双模式门禁

开始编码前确认模式：单人未声明多人时保持串行；用户明确多人开发时，读取《多人协作》给出的当前分支、目标 base、负责人、vault/任务范围、依赖分支和共享契约。仅凭多个分支不能自动认定多人。

多人模式下，修改公共 API、类型、数据库迁移、权限、安全、配置语义或共享模块归属前，先通知协调 overlay。若两个活跃分支对功能行为不一致，停止实现并把双方证据、下游影响和 2–3 个选项交用户决定。

完成链固定为：

```text
普通多人模式：实现 → 实现者自审 → 测试 → 标记待审 → 《代码审查》 → 用户选择 → 《分支合并》
Goal 多人模式：实现 → 实现者自审 → 测试 → 标记待审 → 《代码审查》 → 按启动合同返回监工 → 《分支合并》
```

《代码审查》按改动定级执行（§二之二 L0/L1/L2）：L0 微改动自审标记 `L0-SKIP` 即可通过，L1 走简化审查，仅 L2 走完整 6 项审查。多人模式不得把应定 L2 的改动降级以绕过独立审查。

本内部流程 不审查自己的变更来替代独立审查，也不自行合并、push 或删除分支。审查发现需修改时按问题类型回到《项目开发》《Bug修复》《需求修改》或《重构协调》。每次只处理已确认的一个分支/任务。
