
# 遗留项目接入（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时补齐脚手架；作为 `ASSISTING` 时只返回代码现状证据。重复加载默认从最近阶段恢复，切换时保留扫描范围、推断项和已生成文档，外部输入不得扩大写入范围。

把已有源码逆向整理为与《项目初始化》一致的最小脚手架，使项目可以继续由《项目开发》驱动。

- 《项目初始化》从用户需求规划未来项目。
- 本内部流程 从现有代码归纳当前事实，并向用户确认代码无法表达的业务意图。

---

## 适用场景

- 工作目录已有可观源码和可识别的依赖或构建清单。
- `项目备忘录.md`、`docs/`、`vault/` 至少一项缺失或明显不完整。
- 用户要求“接入老项目”“逆向补文档”“让现有仓库进入项目开发流程”。

**不适用：**

- 空白目录 → 《项目初始化》。
- 脚手架完整，只需继续实现 → 《项目开发》。
- 脚手架完整，只想检查是否过期 → 《文档与项目同步检查》。
- 只想寻找技术债或重构候选 → 《重构机会寻找》。
- 已明确需求变化或 Bug → 分别使用《需求修改》或《Bug修复》。

---

## AI 行为总纲

1. **以代码和配置为实现事实源**：不得凭项目名臆造功能、接口或架构。
2. **业务意图由用户确认**：无法从代码确定的目标、历史原因、勿动范围和未来规划标记“待确认”。
3. **只补脚手架**：不修改业务源码，不顺手重构或修 Bug。
4. **默认主 Agent 串行**：先建立索引，再按命中范围深读；只有仓库较大且扫描域互相独立时，才使用 1–2 个只读子 Agent。
5. **失败可接管**：子 Agent 超时或中断后，主 Agent可以继续该扫描域，不重复已完成结果。
6. **询问必须交互式提交**：存在业务取舍时提供 2–3 个清晰选项。
7. **中间报告不强制落盘**：勘探和扫描摘要默认留在对话中，最终脚手架必须落盘。

## 前置检查

- [ ] 存在源码入口或可识别的源码目录。
- [ ] 存在依赖/构建清单，如 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml` 或 `Cargo.toml`。
- [ ] 已盘点 `项目备忘录.md`、`docs/`、`vault/` 的缺失与可复用内容。
- [ ] 已识别依赖目录、生成物和构建产物，扫描时默认排除。

目录实际为空或只有 README/.gitignore → 停止并转《项目初始化》。

## 阶段一：勘探与范围确认

先用只读方式建立基线：

- 技术栈、版本、数据库、中间件。
- 项目类型、入口、启动和构建脚本。
- 顶层目录及疑似职责。
- 测试框架、测试目录和可识别的测试命令。
- 已有文档和可复用内容。
- 近期活跃范围；有 Git 历史时可参考，没有时不得虚构。

仅对代码无法回答的问题使用交互式问答：

- 项目的一句话定位和核心业务目标。
- 未体现在代码中的安全、性能或合规要求。
- 已知勿动模块和历史兼容约束。
- 接入后最希望继续开发或重构的方向。
- 是否按增量任务评估最小上线版本和 V0 路线。
- 前端现状（如适用）：页面、路由、导航、角色、组件库、视觉约束和大陆网络资源依赖。

在对话中输出基线摘要和待确认项。信息足够时直接进入下一阶段，不要求每阶段单独确认。

## 阶段二：扫描归纳并补齐脚手架

### 2.1 扫描范围

按需扫描以下领域：

| 领域 | 事实来源 | 归纳内容 |
|---|---|---|
| 模块与依赖 | 源码目录、导入和入口 | 模块职责、边界、依赖关系 |
| 接口与数据 | 路由、控制器、DTO、schema、ORM、迁移 | 接口、类型、实体与约束 |
| 项目约定 | 公共工具、异常、日志、分页、ID、时间实现 | 当前实际约定 |
| 配置与环境 | 配置加载、脚本、容器文件、`.env*` | 变量名、启动方式和默认配置 |
| 测试与质量 | 测试、lint、格式化、CI 配置 | 测试范围、质量工具和验证入口 |

区分“代码确认事实”和“推断”。推断项必须显式标注，并在影响脚手架决策时让用户确认。

### 2.2 目标结构

```text
项目根/
├── 项目备忘录.md
├── docs/
│   ├── 需求与架构.md
│   ├── 开发进度.md
│   └── 接口.md            # 复杂项目按需
├── vault/
│   ├── 00-存量-模块.md     # 关键存量模块按需
│   └── 10-增量任务.md      # 接入后新增任务
└── .env.example           # 项目需要环境变量时
```

复用 `references/project-init.md` 中已有模板和软上限，不另建生产版文档矩阵。

### 2.3 文档生成规则

#### `项目备忘录.md`

包含项目概述、技术栈、核心约定、模块依赖图、文档指针、勿动文件和 Git 规范。内容保持可快速读取，目标不超过 150 行。

#### `docs/需求与架构.md`

顶部注明：

```markdown
> 本文档依据现有代码库逆向梳理当前状态（as-is），不是原始需求记录；标注“待确认”的内容需要持续校正。
```

写入当前功能、技术栈、模块边界、数据模型、接口速查、部署环境和待确认项。复杂接口才拆出 `docs/接口.md`。

#### `docs/开发进度.md`

- 关键存量模块标 `✅ 已完成`，备注“存量，逆向接入”。
- 已确认的增量任务标 `⬜ 待开发`。
- 若增量任务有效 vault 数量大于 3，接入完成前切换至《最小上线标准评估》内部流程和《版本功能分割》；存量事实不计入阈值。
- 无法仅凭仓库判断是否完成时，标记“待确认”，不得因文件存在就断言功能完成。

#### `vault/*.md`

存量和增量分轨：

- `00-`～`09-`：关键存量模块档案，按需创建，不要求每个目录一份。
- `10-` 起：接入后的增量任务，使用《项目初始化》的标准 vault 模板。

存量档案至少包含职责、现有实现文件、接口与类型、约束、测试现状和状态。发现坏味道只记录为现状；需要系统评估时建议切换至《重构机会寻找》内部流程，不在接入过程中执行重构。

#### `.env.example`

只写代码真实读取的变量名、用途和安全占位值。禁止复制真实 token、密码、连接密钥或私密地址。

## 阶段三：复核与交接

完成前快速核对：

- [ ] `项目备忘录.md`、`docs/需求与架构.md`、`docs/开发进度.md` 和 `vault/` 已就位。
- [ ] 文档中的源码、脚本和配置路径真实存在，无明显悬空引用。
- [ ] 技术栈和版本与依赖/构建清单一致。
- [ ] 关键接口、类型和数据模型已抽样对照真实定义。
- [ ] vault 编号、依赖和开发进度互相对应。
- [ ] `.env.example` 不遗漏已确认变量，不含秘密值。
- [ ] 推断项仍明确标注，没有被写成既定事实。
- [ ] 如有前端，页面/路由/视觉现状已记录；缺失的产品决策切换至《前端页面规划》内部流程或《前端视觉统一》。
- [ ] 备忘录和 vault 符合 lite 软上限。

发现不一致时只修正文档，不改源码。复核完成后输出：

```markdown
遗留项目接入完成。
- 已创建/补齐：
- 保留的待确认项：
- 存量模块：
- 推荐增量任务：
- 下一步：可在同一会话切换至《项目开发》内部流程
- 可选复核：需要更完整审计时切换至《文档与项目同步检查》内部流程
```

完整同步检查是可选的独立诊断，不是接入完成的强制门禁。

---

## 完成标准

- 最小 lite 脚手架能够被《项目开发》直接读取。
- 文档内容有代码、配置或用户确认作为依据。
- 存量与增量任务清晰分开。
- 没有修改业务代码，也没有自动创建重构或 Bug 修复任务。
- 不要求清空上下文，可直接继续后续流程。

---

## 反模式

- ❌ 不扫描代码就臆想需求和架构。
- ❌ 把当前架构改写成理想架构，与真实代码脱节。
- ❌ 强制多 Agent、强制五轮确认或强制落盘中间报告。
- ❌ 为个人项目创建庞大的生产版文档和交接目录。
- ❌ 把每个存量模块都变成待开发任务。
- ❌ 用真实秘密值生成 `.env.example`。
- ❌ 未确认的推断被写成事实。
- ❌ 接入过程中顺手修改业务代码、重构或修 Bug。


## Git 与协作现状识别

接入阶段只读识别仓库实际默认分支、现有分支命名、活跃分支、独有提交和可能的并行工作。多个分支、近期提交或命名模式只构成“疑似多人协作”证据；必须询问用户确认负责人和用途，不能把个人临时或陈旧分支当团队分支。保留已有合理规范，不在接入阶段 checkout、创建、改名、删除、rebase、merge 或 push。确认多人模式后，把证据和待确认项切换至《多人协作》内部流程协调。
