
# 需求修改（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 且用户确认影响清单后修改文档；作为 `ASSISTING` 时只返回文档影响。重复加载恢复已确认清单和修改进度，切换时保留未处理项；外部输入不得授权代码修改或扩大同步范围。

普通模式由主 Agent 串行完成“澄清&评估 → 同步修改 → 确认”，不建变更单或独立影响评估文件，也不做形式化多 Agent 调度。Goal 模式由一个第 1 层执行 Agent 完成同一串行流程，必要时可按根规则同时委派 1 个第 2 层局部 Agent；第 0 层只接收影响清单、证据指针和压缩结果。

---

## 适用场景

- 已使用《项目初始化》或《遗留项目接入》完成脚手架
- `项目备忘录.md`、`docs/`、`vault/` 已就位，部分模块可能已完成
- 用户提出新增/修改/删除功能，或调整技术栈、性能等
- 《文档与项目同步检查》已确认某个 `SYNC-*` 发现属于文档、vault 或进度落后，需要按既定事实同步
- 《重构协调》已确认某个重构候选需要先调整需求、架构、接口或任务文档

**不适用：**
- 空项目 → 用《项目初始化》
- 纯代码 bug 修复（无需求变化）→ 走《Bug修复》
- 已完成模块单纯需要改实现 → 走《项目开发》"已完成模块的修改规则"

## 前置检查

- [ ] `项目备忘录.md` 存在
- [ ] `docs/需求与架构.md`、`docs/开发进度.md` 存在
- [ ] `vault/` 下有模块任务

任一缺失 → 停止，提示用户先完成初始化或遗留接入。

## 阶段一：澄清 & 评估（一轮对话内完成）

### 1.1 澄清变更内容

主动追问必须采用交互式问答提交给用户（必要时给 2-3 个选项让用户挑）：
- **变更类型**：新增 / 修改 / 删除 / 调整非功能要求 / 调整技术栈/依赖 / 调整数据模型或接口
- **变更描述**：具体改成什么、为什么改
- **优先级**：是否阻塞当前开发？是否允许回退已完成模块？
- **版本归属**：加入当前 V0、后续版本，还是替换当前版本已有功能？
- **上线标准**：是否改变最小上线标准或当前版本完成定义？
- **前端范围（如适用）**：页面、路由、导航、用户流程、共享组件、视觉 token、响应式和可访问性。

> 不需要建 `docs/变更单/CR-*.md` 这种 ID 化文件。澄清结论直接在对话里复述给用户确认。

### 1.2 评估影响（对话内表格）

若输入包含 `SYNC-*`，复用其双侧证据、建议权威来源、置信度和处理边界，只验证本次准备修改的对象。除非已有明确需求依据或用户确认，不得默认用源码覆盖需求文档；诊断发现也不构成批量修改授权。

当前执行者读取 `项目备忘录.md` + 受影响 vault + `docs/需求与架构.md` 相关段，在**对话里**列出影响清单。普通模式的执行者是主 Agent；Goal 模式的执行者是第 1 层 Agent，读取结果不得回灌第 0 层：

```markdown
## 本次变更影响清单

### 目标/版本影响
- 当前目标与非目标：
- 当前版本/后续版本：
- 版本目标是否变化：
- 最小上线标准/完成定义：

### 页面与视觉影响
- 页面/路由/导航：
- 用户流程与权限：
- 共享组件与设计 token：
- 响应式/可访问性/视觉回归：

### 文档影响
- docs/需求与架构.md：[需要改哪段]
- docs/开发进度.md：[哪些行需要回退/新增/删除]
- 项目备忘录.md：[勿动清单 / 文档指针 是否需要更新]

### vault 影响
| vault | 当前状态 | 影响 | 处理 |
|---|---|---|---|
| 02-数据模型.md | ✅ 已完成 | 新增字段 X | 从勿动清单移除，回退为 ⬜，建 02a 子任务 |
| 03-认证.md | 🚧 进行中 | 接口签名变化 | 暂停，修改 vault 后重新开始 |
| 06-新模块.md | — | 新建 | 新增 vault 文件 |

### 接口/数据/配置
- 接口（docs/接口.md 或 vault 内接口段）：[新增/修改/删除清单]
- 数据模型：[字段增删]
- .env.example：[新增/删除变量]

### 已完成模块返工评估
（若涉及已完成模块，列出返工范围和风险点；无则写"无"）

### 处理建议顺序
1. 若 V0/最小上线范围变化，先切换至《最小上线标准评估》内部流程并由用户确认
2. 切换至《版本功能分割》内部流程生成版本与 TODO 映射
3. 若有页面/导航决策，切换至《前端页面规划》内部流程；若全局视觉变化，切换至《前端视觉统一》内部流程
4. 改 docs/需求与架构.md
5. 改 vault
6. 改 项目备忘录.md（依赖图/勿动清单）
7. 改 docs/开发进度.md（状态、版本、上线阻断和证据）
```

普通模式用交互式问答向用户确认：**“以上是影响范围。是否按此清单同步修改文档？需要调整范围请指出。”** Goal 模式中，启动合同已精确覆盖该变更类型、对象和文档范围时视为已确认，不重复询问；目标、版本、产品语义或范围变化则交回 Goal 作为完全阻断升级。

**用户确认或有效 Goal 合同形成前禁止改任何文件。**

## 阶段二：同步修改（当前执行者串行落盘）

只改影响清单中**实际命中**的文档，不做全量六项串行；本阶段不并行写入。Goal 模式如需第 2 层调研或核对，必须先返回第 1 层再由其串行修改：

1. **改 `docs/需求与架构.md`**：更新对应段落（如有大幅变化，在段首加一行 `> 变更于 YYYY-MM-DD：[一句话]` 留痕）。
2. **改受影响的 vault 文件**：
   - 修改已存在 vault 的相应章节（实现要点 / 接口与类型 / 测试要点等）
   - 新增 vault 文件按《项目初始化》2.3 模板写
   - 未开始、从未进入已确认版本且没有实现证据的 vault 可删除
   - 已进入版本计划、已有实现证据或已完成的 vault 不直接删除：标记取消/移至后续版本，或创建 `02a` 增量返工任务保留历史
   - 对**已完成**的 vault，若需返工，建子任务 vault（如 `02a-用户模型扩展.md`），不要直接改原文件；并在原文件末尾加一行 `> 后续返工见 vault/02a` 留痕
3. **改 `项目备忘录.md`**（仅当命中时）：「勿动文件」清单中受影响的项移除；必要时更新文档指针
4. **改 `docs/开发进度.md`**：
   - 已完成 → 回退为 ⬜（或建 02a 子任务行）
   - 进行中 → 标 🚫 阻塞 + 备注"等待变更同步"
   - 新增 → ⬜ 待开发
   - 删除 → 仅对未承诺且无实现证据的任务移除；其余标记取消/移版并保留记录
5. **接口同步**：接口变化只回写受影响 vault 的「接口与类型」段（唯一事实来源）；仅当项目按需建了 `docs/接口.md` 时才同步它。
6. **`.env.example`**（仅当变量增删时）：增删变量。

全部改完后在对话里一次性汇总改动清单，不逐项报告。

## 阶段三：确认

以下 1–2 项为执行者自查项，发现不一致直接修复，不需要逐条向用户汇报；仅当发现第 3 项层面的矛盾或需要扩大已确认范围时，才升级给用户。

- [ ] vault 编号 vs `docs/开发进度.md` 行一一对应、无悬空；删除的 vault 没有被其它文档引用
- [ ] 本轮选定的 `SYNC-*` 发现均已消解，或明确保留为待确认；不顺手处理未获授权的其它发现
- [ ] 版本路线、任务版本归属、上线阻断和验收标准互相对应（矛盾时升级用户）

发现不一致 → 直接修。

完成后告诉用户：

> "需求变更同步完成。可以继续《项目开发》——建议优先处理：[列出新增/回退的关键 vault 编号]。同会话可直接继续，也可清空上下文重新丢《项目开发》+ `项目备忘录.md`。"

## 关键提醒

1. **本内部流程 不写业务代码**：只改文档；代码层修改交给《项目开发》；若是明确 bug 修复，交给《Bug修复》。
2. **影响评估先于动手**：未列清影响清单前不准改文件。
3. **已完成模块优先用子任务（02a）增量返工**，不要整体回退原 vault，避免破坏已通过的测试。
4. **技术选型仍要用户拍板**：变更涉及多个技术路线时，用交互式问答列 2-3 方案 + 利弊。
5. **不强制 CR 编号**：个人项目不需要建 `docs/变更单/CR-*.md` 文件。
6. **不强制 `docs/修复记录.md` 留档**：在对话里告诉用户一句即可。

## 反模式

- ❌ 没列影响清单就直接动文件。
- ❌ 单独建 `docs/变更单/` 给每次变更编 ID。
- ❌ 把"已完成"模块整体回退为 ⬜，无视子任务方案。
- ❌ 只改了 vault 接口段，忘记同步 `docs/接口.md` 或反过来。
- ❌ 在本内部流程 里动手写业务代码。
- ❌ 普通模式派一堆 R1~R6 / W1~W6 子 Agent 走形式；Goal 模式突破三层结构或 `2 × 1` 同时委派上限。


## 多人协作门禁

若变更影响活跃分支共享的 API/类型、数据迁移、权限安全、配置语义、共享模块或测试期望，先通知《多人协作》并列出受影响分支与负责人。分支间功能冲突必须停止，由用户决定业务行为；本内部流程 不能按当前分支视角自行裁决。文档同步完成后，各实现分支仍须独立《代码审查》，并由用户逐个批准《分支合并》。
