
# 分支合并（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

一次只处理一个明确的源分支到一个明确目标分支。该内部流程是有界 Git 写流程，不是全自动发布。普通模式下每个高影响动作都有独立门禁；Goal 模式下，启动合同已精确列出的源/目标/策略、merge、push 和清理动作视为已确认，不再重复询问。结束后恢复原 `ACTIVE` 流程或《多人协作》协调表。

## 一、精确范围

开始前确认：源分支、目标分支、预期策略（merge / squash / rebase 后合并等）以及本次是否只做本地合并。不得假定目标是 `main`。多个候选或用户只说“合并完成的”时，先切换至《多人协作》内部流程列候选并让用户只选一个。

## 二、只读预检

在任何 Git 写操作前检查并解释：

- 工作区是否干净，是否有未完成 merge/rebase/cherry-pick；
- 源/目标 ahead/behind、独有提交和变更范围；
- 独立《代码审查》结论与当前测试证据：已有 `L0-SKIP` 标记或当前有效的 `APPROVE` 结论（基线未变、无新提交）时直接引用，不重新审查；仅当基线变化、或结论为 `CHANGES REQUIRED` 后修复时，重新审查相关变更；未知即未知；
- 依赖分支是否已集成；
- 潜在机械冲突与功能冲突；
- 是否需要 fetch（网络动作需说明并获授权）。

预检不通过时停止并给处理选项，不擅自 stash、reset、丢弃或覆盖改动。

## 三、展示计划并逐步确认

计划至少包含：精确源/目标、策略、预计提交结果、验证命令、冲突处理边界、是否 push、是否清理。普通模式下必须分别获得；Goal 模式仅当下列项目未在启动合同中精确确认时再询问：

1. 源/目标/策略确认；
2. 执行本地合并确认；
3. 若有机械冲突，对具体解决方案的确认（若合并计划已一并展示全部可预见机械冲突的拟采用方案且用户批准了计划，执行时不再逐处重复确认；仅计划外新冲突单独确认）；
4. 本地验证完成后的 push 确认；
5. push 后删除本地/远程分支的单独确认。

**批量授权选项**：普通模式可在计划展示后选择一次性打包授权"按上述计划执行 merge + 本地验证"，或显式授权"merge + push"二合一。批量授权只覆盖本次已展示计划的分支与动作；出现计划外的新冲突、功能冲突或验证失败时立即中断，回到逐步确认。历史改写、删除分支、下一分支永远不在批量授权范围内。

本地 merge 许可不等于 push、删分支、历史重写或处理下一分支；只有 Goal 启动合同逐项列明的动作才可连续执行。rebase、reset、force push 等历史改写必须单独说明影响并明确批准；默认不做。

## 四、冲突分类

- **机械冲突**：同一区域编辑但意图兼容。展示冲突文件、双方内容和拟采用方案，获批后才解决。
- **功能冲突**：业务规则、公共 API/类型、迁移、权限安全、配置语义、共享模块归属或测试期望不一致。立即停止，不写入折中结果；展示中立证据、下游影响和 2–3 个选项，请用户决定。必要时返回《需求修改》《Bug修复》或《重构协调》，重新审查后再合并。

## 五、执行与验证

只执行批准的一个分支和动作。合并后运行计划中的相关测试/检查，核对提交图和工作区状态。失败则停止，保留可恢复状态并报告，不以修改测试或扩大范围掩盖失败。

本地成功后报告合并结果、验证结果和剩余风险。普通模式下仅在分别获批后执行 push 与分支删除；Goal 模式下仅执行启动合同已列明的精确 push/清理动作。完成后刷新《多人协作》进度表；普通模式由用户选择下一项，Goal 模式按合同返回监工继续调度。

反模式：一次授权连合多支；默认目标为 `main`；未审查就合并；自动裁决功能冲突；自动 stash/reset/force；本地成功即 push；push 后自动删分支；把审查通过等同于合并许可。
