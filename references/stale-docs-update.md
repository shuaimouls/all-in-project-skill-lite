
# 陈旧项目文档更新（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 且用户确认更新计划后写文档；作为 `ASSISTING` 时只返回差距证据。本流程只改文档，不改业务源码。

把按旧版约定（或干脆缺失）的项目文档迁移到当前 lite 文档约定：单一事实来源、纯指针备忘录、vault 无版本段、进度表承载版本归属、内容就绪（无禁词、无模板残留）。适用于本 skill 组旧版本生成的项目，也适用于手工维护多年、结构漂移的文档体系。

---

## 适用场景

- 项目已按本 skill 组旧版本生成 `项目备忘录.md`、`docs/`、`vault/`，但仍是旧约定：备忘录含模块依赖图/技术栈摘抄、vault 含「版本/上线关系」段、存在默认创建的 `docs/接口.md`、备忘录 > 80 行。
- 文档存在但骨架化：正文含"待补充/后续完善/TODO/略/占位"、模板残留、空栏目、关键表格无数据。
- 多份文档重复记录同一信息（接口、版本归属、依赖关系各写一遍），且已互相漂移。
- 用户要求"把旧文档按新约定更新""把文档整理成新版模板"。

**不适用：**

- 空项目 → 《项目初始化》。
- 脚手架整体缺失、只有源码 → 《遗留项目接入》。
- 只想诊断文档与实现是否漂移、暂不改 → 《文档与项目同步检查》。
- 已知具体需求变化要同步 → 《需求修改》。
- 文档与实现漂移需要裁决哪方正确 → 先《文档与项目同步检查》裁决路由，本流程只按已确认事实更新。

---

## 前置检查

- [ ] `项目备忘录.md`、`docs/`、`vault/` 至少部分存在
- [ ] 存在依赖/构建清单或可识别源码，可作为填实内容的事实来源
- [ ] 用户已说明迁移目标（默认：当前 lite 约定）与范围（全项目 / 指定文档）

文档与实现之间的事实漂移（`CODE_DRIFT` / `CONTRACT_DRIFT` 类）不在本流程裁决范围内：先转《文档与项目同步检查》输出 `SYNC-*`，由用户确认权威来源后再回本流程。

---

## 阶段一：只读盘点与差距清单

只读扫描全部现有文档，对照新约定逐项判定。对话内输出差距清单：

```markdown
## 文档约定差距清单

### 结构差距（模板/组织层）
| 文档 | 现状 | 新约定 | 处理 |
|---|---|---|---|
| 项目备忘录.md | 含模块依赖图段、技术栈摘抄，152 行 | 纯指针 ≤ 80 行 | 重写为指针版 |
| vault/02-数据模型.md | 含「版本/上线关系」段 | 改为一行指针"见进度表本任务行" | 删段换指针 |
| docs/接口.md | 默认创建，与 vault 接口段重复且已漂移 | 废弃（或 API ≥10 时改为清单） | 合并入 vault 后删除/重建 |

### 内容差距（空洞/禁词层）
| 文档 | 命中 | 填实来源 |
|---|---|---|
| vault/03-认证.md | 「实现要点」只有栏目名 | 读 src/auth/ 源码归纳 |
| docs/需求与架构.md | 上线标准表"验证方式"列为"待定" | 从 README/测试命令提取 |

### 冗余差距（重复记录层）
| 信息 | 重复位置 | 保留处 | 其余处理 |
|---|---|---|---|
| 接口定义 | 需求与架构速查 + docs/接口.md + vault | 各 vault「接口与类型」 | 速查改指针，接口.md 删除 |

### 待用户裁决
- [无法仅凭代码/文档确定的内容，列 2-3 选项]
```

填实内容的优先级：**源码与配置事实 > 用户确认 > 标注"待确认"**。不得为消灭空洞而臆造内容；无法确定的保留为显式"待确认"小节条目（这是唯一合法的未定标记）。

用户确认差距清单与处理方案前**禁止改任何文件**。

---

## 阶段二：按新约定迁移（串行落盘）

按确认的顺序逐文档处理；每个文档改写后立即过一遍就绪自检再进下一个：

1. **合并冗余**：把漂移的重复信息（接口、版本、依赖）统一到唯一事实来源；被合并处改为一行指针。`docs/接口.md` 若确认废弃，先核对其中独有信息已迁入对应 vault，再向用户单独确认删除（删除文件属不可逆动作，必须单独批准）。
2. **重写 `项目备忘录.md`** 为指针版（≤ 80 行）：项目概述、技术栈与约定指针、文档指针、勿动文件、Git 规范、文档级别、当前目标版本。
3. **改写各 vault**：删「版本/上线关系」段换指针行；「接口与类型」以源码为准补全签名；「实现要点」≥3 条可指向具体路径/类型的内容；「测试要点」≥1 条具体场景；「产出清单」核对真实路径。
4. **改写 `docs/需求与架构.md`**：「接口速查」改指针；关键表格（目标/上线标准/版本路线）填实真实数据行；验证方式列填具体命令或手工步骤。
5. **改写 `docs/开发进度.md`**：确认版本/批次、上线阻断、验收/证据列成为版本归属唯一事实来源；L0 级项目可同步降级为精简列。**若旧版进度表已膨胀（> 120 行或含历史版本任务明细/工作日志段），同步按《项目初始化》§2.4 重构为「进行中 + 当前版本已完成 + 历史版本归档」三段结构**：历史版本任务明细压缩为每版本一行摘要，工作日志和过程性段落直接删除，过程证据若不在 vault 中则先补入对应 `vault/*.md` 再删。
6. **全文禁词清零**：对 `docs/`、`vault/`、`项目备忘录.md` 检索"待补充 / 后续完善 / 后续补充 / TODO / TBD / 略 / 占位 / placeholder / 模板残留"，逐项填实或转为显式"待确认"条目。

全部改完后在对话里一次性汇总改动清单，不逐项报告。

---

## 阶段三：就绪复核（逐项举证）

复用《项目初始化》§2.5a/2.5b 复核标准，逐条在对话中输出证据（命中的文件与行），不接受笼统的"已检查"：

- [ ] 结构复核：备忘录 ≤ 80 行；vault 顶部 3 行齐全；编号与依赖无悬空；进度表含全部任务
- [ ] 禁词全文检索零命中
- [ ] 模板占位文字全部替换
- [ ] 关键表格（目标/上线标准/版本路线）各有 ≥1 行真实数据
- [ ] 每个 vault 四段（接口与类型/实现要点/测试要点/产出清单）填实
- [ ] "待确认"仅存在于显式小节，且逐条标注原因
- [ ] 单一事实来源成立：同一信息只有一处实质记录，其余为指针

任一不通过 → 就地修复后重查。全部通过后输出迁移摘要：已改文档、已删文档（经批准）、保留的待确认项、建议下一步（通常可直接切换至《项目开发》或《Goal监工》）。

---

## 关键提醒

1. **只改文档**：发现实现层面的问题时只记录并路由（《Bug修复》/《重构协调》/《需求修改》），不在本流程顺手修代码。
2. **删除文件单独批准**：废弃 `docs/接口.md` 等删除动作必须逐文件向用户确认，不随差距清单的批量确认自动获得。
3. **不臆造内容**：填实优先依据源码事实；业务意图类内容问用户；仍无法确定的留显式"待确认"。
4. **保持 Git 纪律**：迁移改动按 `docs(scope): ...` 提交；不夹带任何代码改动。

---

## 反模式

- ❌ 不盘点就直接按新模板重写，把旧文档中的独有信息冲掉。
- ❌ 为消灭空洞用套话填实（"注意性能""保证质量"这类无宾语条目视为空洞）。
- ❌ 把多份漂移的重复记录互相抄来抄去，而不是统一到唯一事实来源。
- ❌ 批量确认时夹带删除文件，未单独获得删除批准。
- ❌ 迁移过程中顺手改业务代码、修 bug 或重构。
- ❌ 复核时笼统自报"已检查"，不逐项输出证据。
