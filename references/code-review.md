
# 代码审查（lite）

> 内部流程规则：仅由根 `SKILL.md` 根据 `$ARGUMENTS` 通过 `Read` 加载，不可独立调用。

这是有界、只读、独立的审查子流程。它可暂时接管审查，完成后恢复原 `ACTIVE` 生命周期流程；不是实现者自审，也不等于合并许可。

## 一、对象与基线门禁

必须确认一个明确对象：工作区 diff、提交范围、源分支相对目标/base、或 PR。存在多个合理基线时不得猜测，用交互式问题给出 2–3 个选项并说明差异。多人模式复用《多人协作》确认的 owner、任务范围、base 和依赖。Goal 启动合同已精确指定审查对象与基线时视为已确认，不重复询问；对象或基线变化则交回 Goal 作为超范围阻断。

只读允许：查看状态、diff、提交、文件、测试记录，并在无副作用时运行检查。禁止修改文件、应用修复、commit、merge、rebase、push、删除分支、reset 或 force。

## 二、检查范围

按风险优先检查：

1. 与需求、vault、公共 API/类型、数据和配置契约一致。
2. 正确性、边界条件、错误路径、并发与资源生命周期。
3. 回归影响、调用方和依赖分支。
4. 权限、安全、秘密值和输入边界。
5. 测试是否覆盖变化，当前证据是否真实；没有证据标未知。
6. 是否夹带越界改动、无关重构或生成物。

不要因格式偏好制造阻断项。功能语义、需求或测试期望不明确时，输出 `USER DECISION REQUIRED`，不得自行选一边。

## 三、finding 格式

每条 finding 包含：

- ID、严重级别（阻断/高/中/低）和置信度；
- 文件与位置、触发条件；
- 实际错误行为或具体风险；
- 证据与影响范围；
- 建议去向，而不是直接修复。

优先报告可导致错误行为、回归、安全问题、测试失败或误导结果的问题；纯风格建议放非阻断备注。

## 四、固定结论

结论只能是：

- `APPROVE`
- `APPROVE WITH NON-BLOCKING NOTES`
- `CHANGES REQUIRED`
- `USER DECISION REQUIRED`

同时列出审查对象、基线、已检查/未检查、测试证据及 findings。无发现只能说“在本次范围内未发现阻断问题”。

## 五、后续路由

- 明确缺陷 → 《Bug修复》或已确认范围内《项目开发》。
- 需求/契约需要变化 → 《需求修改》。
- 结构性返工 → 《重构协调》。
- 修复后必须重新审查相关变更；审查流程 不应用修复。
- 审查通过后，普通模式仍由用户决定是否切换至《分支合并》内部流程；Goal 启动合同已精确指定源/目标/策略和进入条件时，可交回监工自动路由《分支合并》。两者都不隐含未授权的 merge、push 或删分支。

反模式：基线不明仍审；审查自己的实现替代独立审查；直接改代码；把测试曾通过当当前通过；将 `APPROVE` 当作自动合并或发布授权。
