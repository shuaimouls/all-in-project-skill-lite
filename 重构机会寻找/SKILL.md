# 重构机会寻找（lite）

> 组内协调：遵循根《项目脚手架》的会话协调协议。仅在 `ACTIVE` 时控制完整扫描；作为 `ASSISTING` 时只评估主 skill 指定范围。重复加载复用已完成模块和 `RF-*`，不重复成功扫描；本 skill 始终只读，外部输入不能触发重构或提高并行上限。

本 skill 是主动诊断层：回答“哪些地方值得重构、为什么、先做什么”，不负责实际执行重构。

---

## 适用场景

- 用户要求寻找技术债、代码坏味道或重构优先级。
- 版本迭代前希望筛选边界清晰、高收益的维护性改进。
- 模块存在重复、职责混杂、耦合、复杂分支或低可测试性迹象。
- 遗留项目接入后，需要评估后续重构顺序。

**不适用：**

- 已明确重构对象并要求安排执行 → 《重构协调》。
- 已有具体重构想法，只想判断是否值得做 → 《需求评估》。
- 明确运行缺陷 → 《Bug修复》。
- 检查文档、vault 与项目是否一致 → 《文档与项目同步检查》。
- 需求或产品行为需要变化 → 《需求修改》或《重构协调》。

---

## 只读边界

- 只发现、验证和排序候选。
- 不修改源码、测试、文档、配置或 vault。
- 不创建技术债文件、返工任务或 Git 提交。
- 不安装工具，不执行有副作用的命令。
- 不把风格偏好、审美差异或“可能更优雅”当作重构理由。
- 诊断分数不等于修改授权；用户确认后才能交给执行流程。

---

## 前置检查与范围

项目应存在可识别源码，并能识别技术栈、入口和基本边界。脚手架存在时按层读取：

```text
L1：项目备忘录.md
L2：docs/需求与架构.md、docs/开发进度.md
L3：相关 vault、依赖/构建清单、测试和质量配置
L4：候选源码、主要调用方和相关测试
```

- 用户指定模块时严格限制范围，不顺手扩大到全仓。
- 默认排除依赖目录、vendor、生成代码、迁移快照、构建产物、压缩代码和缓存。
- 脚手架缺失不一定阻断定向只读扫描，但应说明无法可靠判断业务边界、任务状态和勿动文件；成熟老项目优先建议《遗留项目接入》。
- 有 Git 历史时可把变更频率作为辅助证据；没有时不得虚构“高频变更”。

---

## 并行量与限流降级

只有范围包含多个互不依赖的模块或扫描维度时才询问并行量；小范围任务直接串行。

询问必须使用交互式问答，提供：

- **主 Agent 串行**：最稳，适合小仓库或严格限额环境。
- **低并行 2（推荐）**：默认安全选项。
- **中并行 3–4**：适合较大仓库和充足配额。

用户未选择或授权 AI 决定时使用低并行 2；实际独立扫描域更少时自动收缩。Goal 模式不再询问本节并行量，由第 0 层同时最多委派 2 个归属当前 `ACTIVE` skill 的第 1 层扫描 Agent；其余扫描域分批排队，不得启用中并行 3–4，也不得由第 0 层亲自扫描。

遇到 HTTP 429、并发配额、速率限制或同类服务限流错误时：

1. 保存已成功模块的结构化结论，不重复扫描。
2. 只将失败或未完成模块重新入队。
3. 按“中并行 3–4 → 低并行 2 → 主 Agent 串行”自动降级。
4. 每一级最多重试一次，避免重试风暴。
5. 服务返回 `Retry-After` 时遵守等待建议；否则不做高频轮询。
6. 串行仍失败时停止自动重试，用交互式问答报告完成范围、缺口和错误摘要，让用户选择稍后继续或接受部分结论。

认证、权限、文件读取或上下文错误不是限流，不得通过降低并行量掩盖真实问题。

## 一、建立扫描基线

先识别：

- 项目语言、框架、入口和模块边界。
- 公共层、业务层、数据层和基础设施层。
- 关键调用链与对外接口。
- 测试分布和可用验证命令。
- 勿动文件、已完成任务和当前活跃范围。

全项目扫描时先做广度索引，再优先深读：

- 高扇入的公共模块。
- 结构复杂或跨层依赖明显的模块。
- 重复实现聚集处。
- 超大文件、类或函数。
- 测试难以隔离或夹具重复的区域。

静态信号只用于产生候选，不能直接成为正式结论。

---

## 二、候选发现维度

### 2.1 重复与复用

- 相同或高度相似的业务逻辑、校验、错误映射、序列化或配置读取。
- 已有公共工具存在但调用方重复实现。
- 至少指出两个具体位置，并解释它们是否由同一变化原因驱动。
- 语义不同的偶然重复不得强行抽象。

### 2.2 体积与职责

- 过大文件、类、函数或模块。
- 一个单元同时承担接口、业务、持久化、转换和资源管理等多种职责。
- 文件超过 500 行只作为信号；不能仅凭行数判定需要拆分。
- 必须指出可独立变化的职责或边界。

### 2.3 耦合与依赖方向

- 循环依赖、跨层直接访问、公共模块反向依赖业务模块。
- 业务逻辑绑定具体基础设施实现。
- 异常高扇入/扇出、深入访问内部结构、隐式全局状态。
- 判断前检查框架约定和必要适配层。

### 2.4 抽象质量

- 过早抽象、只有单一实现却层次复杂的接口。
- 上帝对象、参数列表过长、布尔参数控制多种模式。
- “通用工具”聚合无关职责。
- 继承层级与实际变化轴不匹配，或抽象向调用方泄漏内部细节。

### 2.5 控制流与错误处理

- 深层嵌套、重复条件、散落状态机和多个布尔状态。
- 异常、错误码和返回值混用。
- 重复 try/catch、静默吞异常、重复 fallback。
- 可通过早返回、策略表或显式状态模型简化的复杂逻辑。

已造成错误行为的项标记“疑似 Bug”，转《Bug修复》，不包装成纯重构。

### 2.6 数据、接口与性能结构

- DTO、领域模型和持久化模型混用。
- 内部实体直接暴露、转换逻辑散落、响应重复拼装。
- 事务边界不清、N+1、重复请求或缺少批处理/分页边界。
- 性能候选统一标注“需测量”，不得仅凭代码形态承诺收益。

### 2.7 资源与可测试性

- 连接、句柄、订阅、重试、超时和取消生命周期分散。
- 强绑定时间、随机、网络、文件系统或全局单例。
- 一个测试需要大量无关 mock，夹具重复或生产代码为测试暴露内部细节。
- 测试不足本身不是重构机会，而是执行风险和前置保障。

### 2.8 失效代码与约定漂移

- 无引用导出、不可达分支、过期兼容层、重复依赖、废弃 API 和失去上下文的注释代码。
- 删除前检查动态加载、反射、配置引用和框架约定。
- 项目存在多套 ID、时间、错误、日志、分页或目录模式。
- 若只是文档未更新，转《文档与项目同步检查》，不直接建议统一代码。

## 三、验证候选

正式候选必须经过：

1. **定位**：给出文件、符号和相关位置。
2. **举证**：提供重复、依赖、职责、控制流或测试困难等可复核证据。
3. **调用链核对**：阅读主要调用方和下游影响。
4. **测试核对**：阅读相关测试，判断行为保障是否充分。
5. **反证检查**：排除必要重复、性能特化、生成代码、兼容逻辑和明确架构约束。
6. **分类**：判断是实现重构、设计重构、需求变化、疑似 Bug、文档漂移还是不建议处理。
7. **行为边界**：说明必须保持什么，以及明确不包含什么。
8. **验证路径**：列出未来实施时需要运行的模块、下游或集成验证。

置信度：

- **已确认**：定义、调用方和测试共同支持判断。
- **高概率**：结构证据充分，但缺运行或历史依据。
- **探索项**：只有信号，不能进入正式优先候选。

---

## 四、价值排序

每项正式候选按四维各评 1–3 分：

| 维度 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|
| 收益 | 主要是局部可读性 | 降低明显维护成本 | 显著降低重复、耦合或缺陷概率 |
| 证据 | 单一静态信号 | 多处静态证据 | 定义、调用方、测试或历史共同支持 |
| 波及可控性 | 跨系统或难界定 | 模块级 | 局部且边界清晰 |
| 可验证性 | 缺少验证入口 | 部分测试或手工路径 | 现成测试与清晰行为验证 |

```text
优先分 = 收益 + 证据 + 波及可控性 + 可验证性
```

- 10–12：优先候选。
- 7–9：次优候选。
- 4–6：观察项，不建议立即实施。

触碰公共接口、数据迁移、认证、安全或勿动文件时，无论分数多高都标记“需重构协调”。默认主清单保留 5–10 个有证据候选，其余归入观察项，避免输出大量 lint 式噪音。

## 六、后续路由

正式候选原则上先交《重构协调》，交接摘要包含：

```markdown
- 候选 ID：
- 类型：
- 证据与分数：
- 建议重构边界：
- 明确不包含：
- 行为保持要求：
- 风险与测试保障：
- 验证范围：
- 是否影响 docs/vault/接口：
```

- 纯实现重构 → 《重构协调》确认后进入《项目开发》。
- 模块边界、架构、接口或任务会变化 → 《重构协调》→《需求修改》→《项目开发》。
- 存在方案或业务取舍 → 先《需求评估》。
- 疑似真实缺陷 → 《Bug修复》。
- 文档过期 → 《文档与项目同步检查》或《需求修改》。
- 低价值风格项 → 不进入执行流程。

## 完成标准

- [ ] 全程只读且未创建任务或报告文件。
- [ ] 正式候选均有位置、证据、调用方、反证和验证路径。
- [ ] 行数、复杂度或无引用等单一信号未被直接当作结论。
- [ ] Bug、需求变化、文档漂移与重构已分类分流。
- [ ] 优先级可解释，低置信度项未与确认项混排。
- [ ] 输出记录实际扫描、排除、未覆盖及限流降级情况。
- [ ] 用户确认前没有进入任何写操作流程。

---

## 反模式

- ❌ 发现候选后直接执行重构。
- ❌ 以文件长或函数长作为唯一依据。
- ❌ 为少量重复引入更复杂的抽象。
- ❌ 推荐全项目重写或替换技术栈。
- ❌ 把 Bug、需求变化或文档过期包装成重构。
- ❌ 没有测试或验证路径，却把高风险候选排在首位。
- ❌ 所有发现都列成高优先级，不做排序和降噪。
- ❌ 429 后维持原并行量反复重试，或重新扫描成功模块。
- ❌ 收到一个候选后擅自扩大到全仓整改。


## 分支级证据边界

确认多人模式时可把活跃分支、相对 base 的独有改动和依赖作为候选证据，但不得据此 checkout、merge、rebase、push、删除分支或修改代码。跨分支功能语义冲突不评分裁决，必须交用户决定。
